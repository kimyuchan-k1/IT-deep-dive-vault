# B+Tree는 왜 이진 트리가 아니라 수백 갈래로 갈라지나

## 흔한 오해

"인덱스는 결국 이진 탐색 트리 아닌가? 정렬해두고 반씩 좁혀가니까 O(log n)이고."

대부분 그렇게 안다. 자료구조 수업에서 BST, AVL, Red-Black을 배우니 인덱스도 그 연장선이라 생각한다. 그래서 "행이 10배 늘면 비교 횟수도 log만큼만 늘겠지"라고 계산한다.

**틀린 건 아닌데, 가장 중요한 변수를 빼먹었다.** 데이터베이스 인덱스의 적은 비교 횟수가 아니라 **디스크 I/O 횟수**다. 이진 트리는 메모리에선 훌륭하지만 디스크에선 재앙이다. B+Tree가 한 노드를 수백 갈래로 쪼개는 건 바로 이 디스크 I/O를 줄이기 위한 설계다.

## 실제 원리

### 비교는 공짜, 디스크 읽기는 비싸다

핵심 전제부터: CPU가 두 키를 비교하는 데 드는 시간은 나노초 단위다. 반면 디스크(SSD라도)에서 한 블록을 읽어오는 데는 수십~수백 마이크로초. **둘 사이 비용 차이가 1,000배 이상**이다. 그래서 인덱스 설계의 목표 함수는 "비교를 줄이자"가 아니라 "디스크 접근을 줄이자"로 바뀐다.

이진 트리로 천만 개 키를 담으면 트리 높이가 약 log₂(10,000,000) ≈ **24**가 된다. 노드 하나가 디스크 블록 하나에 흩어져 있다면, 최악의 경우 키 하나 찾는 데 24번의 디스크 접근이 필요하다.

### 그래서 노드를 블록 크기에 맞춰 부풀린다

여기가 핵심이다. B+Tree는 **노드 하나의 크기를 디스크 페이지 하나(보통 8KB, MySQL InnoDB는 16KB)에 정확히 맞춘다.**

8KB 페이지에 키 하나가 약 16바이트(키 + 자식 포인터)라면, 한 노드에 들어가는 가지 수(팬아웃)는:

```
8192 bytes / 16 bytes ≈ 512 갈래
```

즉 한 번 디스크를 읽으면 512갈래 중 어디로 갈지 결정된다. 트리 높이를 다시 계산하면:

```
log₅₁₂(10,000,000) ≈ 2.6  →  높이 3~4
```

천만 행이든 1억 행이든 **인덱스 트리 높이는 거의 3~4에서 멈춘다.** 그래서 행을 찾는 데 필요한 디스크 접근이 24번에서 **3~4번**으로 줄어든다. 이게 B+Tree가 "넓고 얕은" 트리인 이유다.

### B-Tree가 아니라 B+Tree인 이유

하나 더. 실무 DB는 순수 B-Tree가 아니라 **B+Tree**를 쓴다. 차이는 두 가지다.

1. **실제 데이터(또는 PK)는 리프 노드에만 둔다.** 내부 노드는 길잡이용 키만 담는다. 덕분에 내부 노드의 팬아웃이 더 커지고 트리가 더 얕아진다.
2. **리프 노드끼리 양방향 링크드 리스트로 연결**돼 있다. 그래서 `WHERE age BETWEEN 20 AND 30` 같은 범위 스캔이 리프를 따라 옆으로 쭉 읽으면 끝난다. 매번 루트부터 다시 내려갈 필요가 없다.

이 두 번째 특성이 정렬·범위·`ORDER BY ... LIMIT`에서 B+Tree가 [[hash-merge-nested-loop-join]]의 해시 인덱스를 압도하는 이유다. 해시는 등호 조회는 빠르지만 순서가 없다.

## 현장 시나리오

커머스 회사의 주문 테이블(5천만 행)에서 특정 쿼리만 유독 느렸다. `created_at`에 인덱스가 분명히 걸려 있는데도 `WHERE DATE(created_at) = '2026-05-01'` 쿼리가 매번 8초 넘게 걸렸다.

원인 사슬은 이랬다:

- `DATE(created_at)`로 컬럼을 함수로 감쌌다 → 인덱스 키는 원본 `created_at` 값으로 정렬돼 있는데, 옵티마이저는 `DATE(...)` 결과로 정렬된 트리를 갖고 있지 않다
- 그래서 B+Tree를 탈 수 없고 **5천만 행 풀스캔(Full Scan)으로 폴백**
- 풀스캔이 버퍼풀을 휩쓸면서 다른 쿼리들의 핫 페이지까지 evict
- 멀쩡하던 상품 조회 쿼리들의 캐시 히트율이 떨어지며 전체 DB 응답이 함께 느려짐

수정은 한 줄이었다. 함수를 컬럼에서 떼어내 범위 조건으로 바꿨다:

```sql
WHERE created_at >= '2026-05-01' AND created_at < '2026-05-02'
```

이제 옵티마이저가 B+Tree 리프를 범위 스캔할 수 있게 됐고, 8초 → 12ms로 떨어졌다. **인덱스가 있느냐가 아니라, 인덱스가 정렬해둔 형태 그대로 조건을 주느냐가 갈림길이었다.**

## 실무 적용 포인트

1. **컬럼을 함수로 감싸지 마라**: `WHERE DATE(col) = ...`, `WHERE col + 1 = ...`는 인덱스를 무력화한다. 조건을 컬럼이 원본 그대로 비교되는 형태(`col >= ... AND col < ...`)로 바꾼다. 함수가 꼭 필요하면 함수 기반 인덱스(`CREATE INDEX ... ON t (DATE(col))`)를 따로 만든다.
2. **카디널리티 낮은 컬럼 단독 인덱스는 의미 없다**: 성별처럼 값이 2~3종인 컬럼은 인덱스를 타도 테이블 절반을 읽는다. 옵티마이저가 풀스캔을 고르는 게 정상. 선택도(distinct 값 / 전체 행)가 보통 5~10% 미만일 때 인덱스가 이득.
3. **복합 인덱스는 왼쪽부터(leftmost prefix)**: `(a, b, c)` 인덱스는 `WHERE a=`, `WHERE a= AND b=`엔 쓰이지만 `WHERE b=` 단독엔 안 쓰인다. 조건 분포를 보고 컬럼 순서를 정한다.
4. **커버링 인덱스로 리프에서 끝내기**: 조회 컬럼이 전부 인덱스에 있으면 PK로 다시 테이블을 찾아가는 비용(랜덤 I/O)이 사라진다. 자세한 건 [[index-skip-scan-covering]].
5. **InnoDB는 PK가 곧 클러스터드 인덱스**: 보조 인덱스 리프엔 PK 값이 들어간다. PK를 UUIDv4처럼 랜덤하게 잡으면 리프 분할이 잦아져 인덱스가 뚱뚱해진다. 단조 증가 PK(또는 UUIDv7)를 권장.
6. **`EXPLAIN`으로 type 확인**: `ref`/`range`면 인덱스 탔고, `ALL`이면 풀스캔. `rows` 추정치가 실제와 크게 다르면 `ANALYZE`로 통계 갱신.
