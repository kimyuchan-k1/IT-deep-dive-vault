분산 시스템에서 "이 이벤트가 저 이벤트보다 먼저 일어났다"를 판단하는 건 생각보다 어렵다. 서버마다 자기 시계를 들고 있고, 그 시계들은 미묘하게 어긋나 있기 때문이다.

## 흔한 오해

> "각 서버 시각을 NTP로 맞추면 되잖아. 이벤트마다 timestamp 박아두고 작은 값이 먼저 일어난 거지."

타임스탬프로 순서를 정하는 건 직관적이다. 그래서 많은 시스템이 처음엔 그렇게 만든다. 두 쓰기가 충돌하면 timestamp 큰 쪽이 이긴다 — 이게 last-write-wins(LWW)다.

틀린 건 아니다. 단일 서버 안에서는 완벽하게 작동한다. 문제는 서버가 여러 대가 되는 순간 "벽시계 시각"과 "사건의 인과관계"가 따로 논다는 것이다.

## 실제 원리

### 물리 시계는 순서를 보장하지 않는다

NTP로 동기화해도 일반 서버 간 시각 오차는 보통 수 ms~수십 ms, 나쁘면 100ms를 넘는다. 클라우드 VM에서는 가상화 때문에 더 튄다. 즉 A서버의 `12:00:00.030`이 B서버의 `12:00:00.010`보다 **실제로는 먼저** 발생했을 수 있다. timestamp만 보면 거꾸로 판단한다.

여기서 핵심은, 분산 시스템에서 필요한 건 "절대 시각"이 아니라 **happened-before 관계**라는 점이다. Lamport가 1978년 논문에서 정의한 `→` 관계다. a가 b보다 먼저 일어났다(a → b)는 건 세 경우뿐이다.

1. 같은 프로세스 안에서 a가 b보다 앞 코드일 때
2. a가 메시지 send이고 b가 그 메시지의 receive일 때
3. a → c 이고 c → b 일 때 (이행성)

이 어디에도 안 걸리는 두 이벤트는 **동시(concurrent)**다. 인과적으로 무관하다는 뜻이지 같은 시각이라는 뜻이 아니다.

### Lamport Clock — 전체 순서는 주지만 인과성은 못 본다

각 프로세스가 카운터 하나를 들고, 이벤트마다 +1. 메시지를 보낼 때 그 카운터를 같이 실어 보내고, 받는 쪽은 `max(내 값, 받은 값) + 1`로 점프시킨다. 이렇게 하면 **a → b 이면 반드시 L(a) < L(b)** 가 성립한다.

그런데 역은 성립하지 않는다. `L(a) < L(b)` 라고 해서 a → b 인 건 아니다. 둘이 그냥 동시일 수도 있다. Lamport clock은 스칼라 하나라서 "더 크다/작다"만 말할 수 있고, "무관하다"를 표현할 방법이 없다. 충돌을 감지해야 하는 상황에선 이게 치명적이다.

### Vector Clock — 인과성과 동시성을 구분한다

프로세스가 N개면 길이 N짜리 벡터를 든다. `VC[i]`는 "i번 프로세스에서 일어난 이벤트를 내가 몇 개까지 봤나". 자기 이벤트엔 자기 칸 +1, 메시지 받으면 칸마다 max를 취한 뒤 자기 칸 +1.

비교 규칙:
- 모든 칸이 `VC(a) ≤ VC(b)`이고 하나라도 작으면 → **a → b** (인과적으로 앞섬)
- 어느 쪽도 다른 쪽을 전부 덮지 못하면 → **동시(concurrent)** = 충돌

여기가 갈림길이다. Lamport는 "둘 중 뭐가 큰가"만 답하지만, vector clock은 "둘이 인과적으로 이어졌나, 아니면 진짜 충돌인가"를 답한다. 충돌 감지가 필요하면 벡터가 필수다.

## 현장 시나리오

Dynamo 스타일 KV 스토어 위에 장바구니를 올린 서비스. 한 사용자가 폰과 노트북에서 거의 동시에 장바구니를 수정한다.

- 폰: 노드 A에 "이어폰 추가" 쓰기, 물리 timestamp `12:00:00.030`
- 노트북: 노드 B에 "충전기 추가" 쓰기, 물리 timestamp `12:00:00.045`

두 쓰기는 서로의 존재를 모른다. 인과적으로 **동시**다. 그런데 시스템이 LWW로 머지하면, timestamp 큰 노트북 쓰기가 이기고 폰에서 담은 이어폰은 **조용히 사라진다**. 사용자는 결제 직전까지 모른다.

vector clock을 썼다면 두 버전이 `{A:1,B:0}`와 `{A:0,B:1}` — 서로 덮지 못하므로 충돌로 감지된다. 그러면 LWW로 하나를 버리는 대신 두 항목을 합집합으로 머지한다(실제 Dynamo가 장바구니에 한 선택). 인과 사슬은 이렇다: clock skew → 물리 timestamp로 잘못된 순서 판정 → LWW가 한 쓰기 폐기 → 담은 상품 유실. 벡터시계 한 번으로 끊긴다.

## 실무 적용 포인트

1. **LWW는 "유실해도 되는 데이터"에만**. 세션 last-seen 같은 건 괜찮지만 장바구니·잔액·문서엔 쓰지 마라. 조용한 데이터 손실이 난다.
2. **NTP 동기화를 순서 보장으로 착각하지 마라**. 동기화는 오차를 줄일 뿐 `happened-before`를 만들지 않는다. 순서가 중요하면 논리 시계를 별도로 둬라.
3. **vector clock 크기 폭증을 경계하라**. 칸이 노드 수만큼 늘어난다. 클라이언트가 수천이면 벡터가 페이로드보다 커진다. **dotted version vector**로 actor를 서버로 한정하거나 주기적으로 pruning.
4. **충돌 머지 로직을 미리 정해둬라**. 감지만 하고 머지 정책이 없으면 그대로 멈춘다. 합집합·set 머지·사용자 선택 중 택1. 자동 머지가 가능한 구조라면 [[crdt-intro]]로 가는 게 정답.
5. **단조성이 깨지면 시계가 거꾸로 간다**. VM 라이브 마이그레이션·NTP step 보정으로 물리 시각이 뒤로 점프할 수 있다. 물리 시각을 직접 쓰는 코드는 단조 시계(`CLOCK_MONOTONIC`)를 써라.
6. **물리+논리 둘 다 필요하면 HLC**. Hybrid Logical Clock은 물리 시각에 논리 카운터를 붙여 "사람이 읽을 수 있으면서 인과성도 보존"한다. CockroachDB가 채택. 단일 스칼라라 vector만큼의 충돌 감지는 못 한다는 한계는 안다.
