# 사이드카를 붙였더니 앱은 그대로인데 p99가 3배 튀었다

## 흔한 오해

"사이드카 패턴은 앱 코드를 한 줄도 안 건드리고 로깅·TLS·재시도·트레이싱 같은 공통 기능을 옆 컨테이너로 떼어내는 거다. 관심사 분리니까 깔끔하고, 앱은 그대로니까 거의 공짜 아닌가?"

서비스 메시 입문 글들이 정확히 이렇게 판다. 앱 옆에 프록시 컨테이너 하나 꽂으면 mTLS, 재시도, 서킷 브레이커, 분산 트레이싱이 마법처럼 생긴다고. 그래서 "비즈니스 로직과 인프라 관심사를 분리했다"며 만족한다.

**관심사 분리는 맞다. "공짜"가 틀렸다.** 사이드카는 코드에서 비용을 걷어내 **런타임으로 옮긴 것**이지 없앤 게 아니다. 앱이 0줄 수정돼도, 모든 네트워크 패킷의 경로가 바뀌고, 파드마다 프록시 한 벌이 CPU·메모리를 먹고, 컨테이너 두 개의 **생명주기가 얽힌다.** 이 셋이 임계를 넘으면 앱은 그대로인데 지연과 비용이 조용히 배로 뛴다.

## 실제 원리

### 사이드카는 같은 파드 = 같은 네트워크 네임스페이스

쿠버네티스 파드 안의 컨테이너들은 **네트워크 네임스페이스와 localhost를 공유**한다. 그래서 사이드카 프록시는 앱과 `127.0.0.1`로 통신할 수 있다. 여기까진 좋다. 문제는 트래픽을 프록시로 **강제로 우회**시키는 방법이다.

Istio 같은 메시는 파드 시작 시 `init container`가 `iptables` 규칙을 심어, 앱이 보내고 받는 **모든 TCP 패킷을 사이드카(Envoy)로 리다이렉트**한다. 그래서 원래 `앱 → 상대 앱` 한 번이면 될 통신이 이렇게 바뀐다:

```
앱A → (iptables) → EnvoyA → 네트워크 → EnvoyB → (iptables) → 앱B
```

호출 한 번에 **프록시를 두 번 더 타는** 구조다. 각 Envoy는 L7에서 패킷을 풀어 헤더를 읽고(라우팅·재시도 판단), mTLS면 TLS 핸드셰이크와 암복호화까지 한다. 이게 모든 요청마다, 양방향으로 일어난다.

### 비용은 세 축에서 동시에 늘어난다

여기가 핵심이다. 사이드카의 비용은 한 군데가 아니라 셋에서 곱셈으로 커진다.

1. **지연(latency)**: 홉이 2개 늘고 매 홉에서 L7 파싱·암복호화가 추가된다. 인메모리 프록시라 보통 한 홉당 **밀리초 미만**이지만, 내부 호출이 체인으로 여러 번 일어나는 마이크로서비스에선 이게 누적된다. A→B→C→D 호출이면 사이드카 홉만 6번이다.

2. **자원(resource)**: 사이드카는 파드마다 **한 개씩** 뜬다. 앱 파드가 500개면 Envoy도 500개다. 프록시 하나가 평소 50~100MB 메모리에 적잖은 CPU를 먹는데, 이게 파드 수만큼 곱해진다. 앱 컨테이너가 200m CPU를 쓰는데 사이드카가 100m을 먹으면 **클러스터 CPU 청구서의 33%가 프록시**가 된다.

3. **생명주기(lifecycle)**: 한 파드 안 두 컨테이너의 시작·종료 순서가 얽힌다. 앱이 먼저 떠서 요청을 보내는데 사이드카가 아직 준비 안 됐으면 그 요청은 실패한다. 종료 때도 사이드카가 먼저 죽으면 앱의 마지막 요청들이 네트워크를 못 탄다. 이건 [[liveness-readiness-startup]] 프로브 설계와 직접 얽힌다.

### 그래서 쿠버네티스가 native sidecar를 넣었다

이 생명주기 문제가 워낙 흔해서, 쿠버네티스 1.28부터 **native sidecar**(restartPolicy: Always인 init container)가 들어왔다. 사이드카가 일반 컨테이너보다 **먼저 시작되고 나중에 종료**되도록 보장해, "앱은 떴는데 프록시가 안 떠서 죽는" 경쟁 조건을 구조적으로 막는다. 사이드카가 공짜였다면 런타임이 이런 1급 기능을 새로 넣을 이유가 없었다.

## 현장 시나리오

40개 마이크로서비스를 운영하는 팀이 "보안 감사 때문에 서비스 간 통신을 전부 mTLS로 바꿔야 한다"는 요구를 받았다. 앱마다 TLS 코드를 넣는 대신 Istio를 깔고 사이드카 자동 주입을 켰다. 앱 코드는 **0줄** 바꿨다. 인과 사슬은 이랬다:

- 사이드카 주입 후 모든 서비스 간 호출이 `앱 → Envoy → Envoy → 앱`으로 바뀜 → 홉당 mTLS 암복호화 + L7 파싱 추가
- 핵심 결제 플로우가 내부적으로 6개 서비스를 체인 호출 → 사이드카 홉만 **12번** → 단순 합산만으로도 지연이 누적
- 평소 엔드투엔드 p99가 **8ms → 25ms**로 상승. 평균은 멀쩡해 보였지만 꼬리 지연이 3배
- 동시에 파드 250개에 Envoy 250개가 뜨며 클러스터 CPU 사용량이 **30% 증가** → 노드 오토스케일러가 노드를 더 띄움 → 월 인프라 비용 상승
- 결정적 사고는 배포 때 터졌다. 롤링 업데이트 중 **앱 컨테이너가 사이드카보다 먼저 종료**되면서, graceful shutdown으로 처리하던 인플라이트 요청들이 네트워크를 못 타고 503으로 떨어짐

원인은 mTLS 자체가 아니라, **"코드를 안 건드린다 = 비용이 없다"는 등식**이었다. 수정은 셋이었다. 자주 호출되는 서비스 쌍은 메시에서 제외해 직접 통신시키고, 사이드카에 현실적인 CPU/메모리 `requests`를 박고, 1.28의 **native sidecar로 전환**해 종료 순서를 보장했다. p99는 14ms로 안정됐다. **사이드카는 비용을 없앤 게 아니라 코드에서 인프라로 옮겨 적은 것**이었고, 옮긴 곳에서 청구서가 날아온 것뿐이었다.

## 실무 적용 포인트

1. **사이드카 자원 요청을 반드시 명시한다**: Envoy 사이드카에 `requests`/`limits`를 박는다(흔히 CPU 100m / 메모리 128Mi 출발선). 안 박으면 best-effort로 뜨다가 노드 메모리 압박 시 제일 먼저 OOMKill 대상이 된다 → [[k8s-pod-death-5-reasons]].
2. **모든 통신을 메시에 넣지 마라**: 초고빈도·초저지연 내부 호출(예: 캐시 조회)은 사이드카 오버헤드가 이득보다 클 수 있다. `PeerAuthentication`을 `PERMISSIVE`로 두거나 특정 포트를 메시에서 제외해 직접 통신시킨다.
3. **종료 순서를 보장한다**: 쿠버네티스 1.28+면 사이드카를 `restartPolicy: Always` init container(native sidecar)로 선언한다. 그 전 버전이면 앱에 `preStop` 훅 + `terminationGracePeriodSeconds`를 줘 사이드카보다 먼저 죽지 않게 한다.
4. **꼬리 지연으로 평가한다**: 사이드카 도입 전후를 평균이 아니라 **p99/p99.9**로 비교한다(평균은 거의 안 변한다). 호출 체인이 깊을수록 홉당 지연이 누적되니 [[distributed-tracing-otel]]로 어느 홉이 먹는지 본다.
5. **프록시 CPU를 따로 모니터링한다**: `istio_request_duration_milliseconds`와 Envoy 컨테이너 CPU를 앱과 분리해 본다. 메시 도입 후 클러스터 총 CPU의 몇 %가 데이터플레인인지 수치로 안다.
6. **대안을 안다**: 파드마다 프록시가 부담이면 **노드당 하나**인 ambient mesh(sidecar-less)나, 공통 로직을 라이브러리(gRPC interceptor)로 넣는 방식과 비교한다. 사이드카는 유일한 답이 아니라 트레이드오프 한 점이다.
