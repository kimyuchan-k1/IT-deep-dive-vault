# 오프라인에서도 되게 만들었더니, 두 사람이 같이 고친 글에서 한쪽 수정이 조용히 사라졌다

## 흔한 오해

"local-first? 그거 결국 오프라인 지원 아닌가. 데이터를 `localStorage`나 IndexedDB에 캐싱해두고, 네트워크 끊기면 로컬에서 읽고 쓰다가, 다시 연결되면 서버로 올려서 동기화하면 되잖아. 충돌? 나중에 저장한 게 이기게 하면 되지."

이 그림은 절반만 맞다. 오프라인 캐싱과 "나중 저장 우선(last-write-wins)"은 **오프라인-퍼스트(offline-first)**의 전형적인 구현이고, 입문 자료도 보통 거기까지 가르친다. 그런데 local-first가 진짜로 풀려는 문제는 "끊겨도 동작하느냐"가 아니라 **"여러 디바이스가 따로 고친 변경을, 중앙 서버 없이도 데이터 손실 없이 합칠 수 있느냐"**다.

`localStorage`에 넣고 last-write-wins로 올리는 순간, 두 사람이 같은 문서를 동시에 고치면 **늦게 도착한 쪽이 먼저 쪽을 통째로 덮어쓴다.** 충돌이 난 게 아니라, 충돌을 **본 적도 없이** 한쪽 작업이 사라진다.

## 실제 원리

local-first는 2019년 Ink & Switch의 에세이가 정립한 개념이다. 핵심은 **데이터의 1차 사본(primary copy)이 사용자 기기에 있고, 서버는 동기화·백업용 보조**라는 것. 그 에세이가 내건 7가지 이상(ideal) 중 운영 난이도를 가르는 건 두 개다 — **"네트워크 없이도 즉시 동작"**과 **"여러 사용자와의 협업"**. 이 둘을 동시에 만족시키려는 순간 분산 시스템의 핵심 문제가 튀어나온다: **중앙 조정자 없이 동시 변경을 어떻게 합치나.**

### last-write-wins가 데이터를 먹는 이유

LWW는 각 쓰기에 타임스탬프를 붙이고, 합칠 때 **타임스탬프가 큰 값만 남긴다.** 단순하고 빠르다. 문제는 "동시(concurrent)" 변경 — 인과 관계 없이 서로 모르고 일어난 두 변경 — 에서 한쪽을 **말없이 버린다**는 점이다.

여기서 "동시"는 벽시계 시각이 같다는 뜻이 아니다. **서로의 변경을 보지 못한 상태**라는 뜻이다([[lamport-vs-vector-clock]]가 다루는 그 인과성이다). A가 오프라인에서 3문단을 고치고, B가 같은 시간 다른 곳을 고쳤다면, 둘은 인과적으로 동시다. LWW는 이걸 구분 못 하고 타임스탬프 큰 쪽만 남긴다. 게다가 기기 시계가 어긋나 있으면(clock skew) **먼저 한 작업이 "더 미래"로 찍혀 이기는** 역전까지 난다.

### CRDT — 합쳐도 결과가 같아지는 자료구조

local-first의 답은 **CRDT(Conflict-free Replicated Data Type)**다. CRDT는 병합 연산이 **교환법칙·결합법칙·멱등성**을 만족하도록 설계된 자료구조다. 즉 변경들이 **어떤 순서로, 몇 번 도착하든** 모든 복제본이 같은 최종 상태로 수렴한다(strong eventual consistency). 중앙 서버가 순서를 정해줄 필요가 없다.

텍스트 편집용 CRDT가 핵심이다. 단순 LWW가 "문자열 통째로 한 값"으로 보는 것과 달리, 시퀀스 CRDT는 **각 문자에 전역적으로 정렬 가능한 고유 식별자**를 부여한다. A가 5번째에 끼운 글자와 B가 같은 자리에 끼운 글자는 **서로 다른 ID**를 갖고, 식별자 순서로 결정론적으로 나란히 배치된다 — 둘 다 살아남는다. 삭제는 진짜 지우지 않고 **묘비(tombstone)**로 표시해, 늦게 도착한 "그 글자 뒤에 삽입" 같은 변경이 갈 곳을 잃지 않게 한다.

### 공짜가 아니다 — 메타데이터와 묘비 비용

CRDT의 대가는 **메타데이터**다. 글자마다 ID를 달고 삭제를 묘비로 남기니, 문서가 실제 텍스트보다 훨씬 커질 수 있다. 그래서 Automerge·Yjs 같은 구현은 **압축(run-length 인코딩, 가비지 컬렉션)**으로 이걸 줄이는 게 엔지니어링의 절반이다. 합치는 정확성은 수학이 보장하지만, **저장·전송 비용을 실용 범위로 누르는 건 구현의 몫**이다.

## 현장 시나리오

오프라인 지원을 자랑하던 협업 메모 앱. 인과 사슬은 이랬다:

- 데이터를 IndexedDB에 저장하고, 문서 전체를 JSON 한 덩어리로 서버에 PUT 하는 구조였다. 충돌 정책은 **last-write-wins**
- 한 PM이 비행기에서 회의록 절반을 오프라인으로 고쳤다. 같은 시간 동료는 사무실에서 같은 문서의 다른 절반을 고치고 저장했다
- PM이 착륙해 와이파이에 붙자, PM의 문서 전체 스냅샷이 **나중 타임스탬프**로 서버에 도착했다. 서버는 그걸 최신으로 받아들였다
- 동료가 사무실에서 쓴 절반이 **통째로 사라졌다.** 에러도, 충돌 경고도 없었다. "저장됨"이라고 떴는데 내용이 없어진 것

운영팀이 로그를 봐도 "충돌"이 잡히지 않았다. LWW는 충돌을 **해결**한 게 아니라 **무시**했기 때문이다. 팀은 문서 본문을 Yjs CRDT로 바꿨다. 그러자 두 사람의 편집이 **문자 단위로 병합**돼 둘 다 남았고, 서버는 전체 스냅샷이 아니라 **증분 변경(update)**만 받아 합쳤다. 원인은 네트워크가 아니라, **순서가 없는 동시 변경을 "순서 있는 한 값"으로 욱여넣은 데이터 모델**이었다.

## 실무 적용 포인트

1. **"오프라인 지원"과 "local-first"를 구분하라**: 단일 사용자·단일 기기면 IndexedDB + LWW로 충분하다. **여러 기기·여러 사용자가 같은 데이터를 동시에 고칠 수 있으면** 그때 CRDT가 필요하다. 협업이 없으면 CRDT는 과한 비용이다.
2. **검증된 CRDT 라이브러리를 써라**: 직접 짜지 마라. 텍스트·리치 협업은 **Yjs**(성능·생태계 강점), 범용 JSON 문서는 **Automerge**가 표준이다. 둘 다 동시 편집 병합과 압축을 이미 푼다.
3. **전체 스냅샷 대신 증분을 동기화하라**: 문서 전체를 PUT 하지 말고 CRDT의 **update/delta**만 교환하라. 대역폭이 줄고, 무엇보다 스냅샷 덮어쓰기로 인한 유실이 원천 차단된다.
4. **묘비·메타데이터 증가를 모니터링하라**: CRDT 문서는 편집·삭제가 쌓이며 커진다. 가비지 컬렉션/압축 주기를 두고, 문서 바이트 크기를 지표로 추적하라. 장수 문서(수년 편집)는 특히.
5. **인과성을 보존하라**: 동기화 프로토콜이 변경의 **causal order**(어떤 변경이 어떤 변경을 봤는지)를 유지해야 한다. [[lamport-vs-vector-clock]]의 벡터 시계류가 "동시 vs 인과 후행"을 구분하는 근거다.
6. **서버를 "권위"가 아닌 "릴레이"로 설계하라**: local-first에서 서버는 변경을 중계·백업하는 역할이지 진실의 원천이 아니다. 인증·접근제어는 그대로 서버에 두되, **데이터 병합 권한을 서버에 독점시키지 마라**.
