# JWT로 갈아타면 세션 서버가 사라진다고 믿었는데, 로그아웃과 강제 차단이 안 돼서 결국 stateful로 되돌아갔다

## 흔한 오해

"세션은 서버가 사용자 상태를 들고 있어야 해서 안 좋다. 로그인한 사람이 늘면 세션 저장소(Redis, DB)도 같이 커지고, 서버를 늘릴 때마다 세션 공유 문제가 생긴다. JWT를 쓰면 **stateless**라 서버는 아무것도 기억할 필요가 없다. 토큰 안에 사용자 정보가 다 들어있고 서명만 검증하면 되니까, 서버를 몇 대로 늘려도 세션 동기화가 필요 없다. 그래서 JWT가 세션보다 현대적이고 확장성 있는 선택이다. 로그아웃? 클라이언트에서 토큰만 지우면 된다."

거의 모든 "JWT vs Session" 글이 이렇게 정리한다. 그리고 절반은 맞다. **검증이 서버 상태 없이 끝난다**는 건 사실이고, 그게 JWT의 핵심 장점이다.

**문제는 그 장점이 곧 약점이라는 것이다.** 서버가 아무것도 기억하지 않는다는 말은, **이미 발급한 토큰을 만료 전에 취소할 방법도 없다**는 뜻이다. 로그아웃, 비밀번호 변경, 계정 차단 — 보안의 핵심 동작들이 전부 "발급된 자격을 즉시 무효화"를 요구하는데, stateless는 바로 그걸 못 한다.

## 실제 원리

세션과 JWT의 차이는 "상태를 어디에 두느냐"가 아니라 **"신뢰의 근거를 어디서 확인하느냐"**다.

### 세션 — 신뢰의 근거가 서버에 있다

세션 방식은 로그인 성공 시 서버가 랜덤한 세션 ID를 만들어 저장소에 박고, 그 ID만 쿠키로 내려준다. 쿠키 안에는 **의미 없는 식별자 하나**뿐이다. 요청이 올 때마다 서버는 그 ID로 저장소를 조회해서 "이 세션이 살아있나, 누구인가"를 확인한다.

여기서 중요한 건 **신뢰의 근거(세션 레코드)가 항상 서버 손안에 있다**는 점이다. 로그아웃은 저장소에서 그 레코드 한 줄을 지우면 끝이다. 다음 요청은 조회 실패로 즉시 거부된다. 강제 로그아웃, 동시 접속 제한, "다른 기기에서 모두 로그아웃" 전부 레코드 조작 한 번이다.

### JWT — 신뢰의 근거가 토큰 자체에 있다

JWT는 정반대다. 토큰은 `header.payload.signature` 세 조각이고, payload에 사용자 ID·권한·만료시각(`exp`)이 들어있다. 서버는 요청이 오면 **서명만 검증**한다 — "이 payload가 내 비밀키로 서명됐고 변조되지 않았나". 검증이 통과하면 payload를 그대로 신뢰한다.

여기가 핵심이다. **검증에 저장소 조회가 없다.** 그래서 빠르고 stateless다. 그런데 같은 이유로, 서버는 **"이 토큰이 아직 유효해야 하는가"를 판단할 근거가 토큰 안에밖에 없다.** 토큰에 박힌 `exp`가 지나기 전까지는, 서버 입장에서 그 토큰은 영원히 정당하다. **이미 누군가 손에 들어간 토큰을 서버가 거부할 방법이 구조적으로 없다.**

### 그래서 stateless 로그아웃은 거짓말이다

"클라이언트에서 토큰을 지우면 로그아웃"은 **공격자가 협조할 때만** 성립한다. 정상 사용자야 브라우저에서 토큰을 버리면 되지만, **토큰을 탈취한 공격자는 사본을 들고 있다.** 서버는 그 사본을 거부할 수단이 없으니, `exp`까지 그대로 살아있다. 이걸 막으려면 결국 서버가 "취소된 토큰 목록(블랙리스트)"을 들고 매 요청 조회해야 하는데 — **그 순간 stateless라는 장점은 사라지고, 세션과 똑같이 stateful이 된다.** JWT를 도입한 이유 자체가 무너지는 것이다.

## 현장 시나리오

한 핀테크 스타트업이 "확장성"을 이유로 세션을 걷어내고 JWT로 전면 전환했다. `exp`는 편의를 위해 **24시간**으로 길게 잡았고, refresh token 회전도 처음엔 안 넣었다. 인과 사슬은 이랬다:

- 한 사용자의 액세스 토큰이 **악성 브라우저 확장**을 통해 탈취됐다. 공격자는 그 토큰으로 API를 정상 호출하기 시작했다
- 사용자가 이상을 느끼고 **비밀번호를 바꾸고 로그아웃**했다. 그런데 서버는 stateless라, 비밀번호 변경이 **이미 발급된 토큰을 무효화하지 못했다.** 로그아웃도 클라이언트 토큰만 지웠을 뿐, 공격자의 사본은 멀쩡했다
- 보안팀이 계정을 **강제 정지**시켰다. 그래도 막히지 않았다 — 토큰 검증 경로에 계정 상태 조회가 없었기 때문이다. 정지 처리는 DB의 `is_active` 플래그만 바꿨고, JWT 검증은 그 플래그를 보지 않았다
- 결국 공격자의 토큰은 **남은 `exp`까지 약 15분(혹은 길면 수 시간) 동안 유효**했다. 그 사이 출금 요청이 나갔다
- 사후 대응으로 팀은 **서명 키를 회전**시켜 전체 토큰을 한 번에 무효화했다. 하지만 그건 **모든 사용자가 동시에 강제 로그아웃**되는 핵폭탄이라, 평상시 차단 수단으로 쓸 수 없었다

수정은 결국 **세션의 장점을 다시 들여오는 것**이었다. 액세스 토큰 `exp`를 **15분으로 짧게** 줄이고, 긴 수명은 **서버에 저장된 refresh token**(취소 가능)으로 옮겼다. 차단·로그아웃은 refresh token 무효화 + 짧은 블랙리스트([[redis-ttl-eviction]]로 `exp`까지만 보관)로 처리했다. 원인은 "JWT가 나쁘다"가 아니라, **무효화가 필요한 자격 증명을 무효화 불가능한 그릇에 길게 담았다**는 것이었다. JWT는 "짧게 살고 자주 갱신되는" 자격일 때만 stateless의 이점을 지킨다.

## 실무 적용 포인트

1. **액세스 토큰 `exp`는 짧게 — 5~15분**: 토큰이 탈취돼도 노출 창을 분 단위로 묶는다. 긴 로그인 유지는 토큰 수명이 아니라 **refresh token**으로 해결하라. `exp` 24시간짜리 액세스 토큰은 "24시간짜리 무효화 불가 비밀번호"와 같다.
2. **refresh token은 서버 저장 + 회전(rotation)**: refresh token은 Redis/DB에 저장해 **취소 가능**하게 만든다. 한 번 쓰면 폐기하고 새로 발급(rotation)하고, 이미 쓴 토큰이 재사용되면 **탈취로 간주해 해당 계열 전체를 무효화**하라(reuse detection).
3. **로그아웃·강제 차단은 블랙리스트로**: 로그아웃 시 토큰의 `jti`(고유 ID)를 블랙리스트에 넣고, 만료 시각까지만 보관(TTL = 남은 `exp`)한다. 매 요청 조회가 부담이면 **액세스는 짧게(블랙리스트 없이도 곧 만료), refresh만 서버 검증**으로 비대칭 설계.
4. **계정 상태를 검증 경로에 포함**: 비밀번호 변경·정지가 즉시 먹히려면, payload에 `pwd_changed_at` 같은 버전을 넣고 검증 시 서버 값과 비교하거나, refresh 시점에 계정 상태를 재확인하라. 서명 검증만으로 끝내지 마라.
5. **서명은 비대칭(RS256/ES256) 우선, `alg:none` 차단**: 검증 서버가 여러 개면 공개키만 배포하는 RS256/ES256가 안전하다. 라이브러리에서 **`alg` 화이트리스트를 고정**해 `alg:none`·HS256↔RS256 혼동 공격을 막아라. 비밀키는 [[mtls-zero-trust]]급으로 관리.
6. **민감 정보를 payload에 넣지 마라**: JWT payload는 **암호화가 아니라 서명**일 뿐 — base64라 누구나 디코드해 읽는다. 주민번호·이메일·권한 상세를 넣지 말고, 식별자와 최소 클레임만. 권한은 [[rbac-abac-rebac]]처럼 서버에서 조회.
