# 프로덕션 서버를 무작위로 죽이는 게 카오스 엔지니어링인 줄 알았는데, 가설도 정상상태 정의도 없는 그건 그냥 장애였다

## 흔한 오해

"카오스 엔지니어링? 넷플릭스 Chaos Monkey처럼 프로덕션에서 인스턴스를 랜덤하게 꺼버리는 거잖아. 시스템이 얼마나 잘 버티나 보려고 일부러 망가뜨리는 거."

대부분 그렇게 안다. 그래서 "우리도 카오스 한번 해보자"가 보통 `kill -9`를 운영 서버에 무작위로 던지는 워크숍으로 변질된다. 무언가 터지면 "거봐, 우리 시스템 약하네" 하고, 안 터지면 "운 좋았네" 하고 끝난다.

**랜덤 파괴는 카오스 엔지니어링의 도구이지 본질이 아니다.** 가설 없이 죽이는 건 통제된 실험이 아니라 그냥 자해성 장애다. 진짜 카오스 엔지니어링은 "정상이 무엇인지 숫자로 먼저 정의하고, 그게 깨질 거라는/안 깨질 거라는 가설을 세운 뒤, 폭발 반경을 좁혀 검증하는" 과학 실험이다.

## 실제 원리

### 출발점은 "파괴"가 아니라 "정상 상태(steady state)"의 정의

카오스 실험은 무엇을 부술지가 아니라 **무엇이 정상인지**를 정하는 데서 시작한다. 정상 상태는 시스템 내부 지표(CPU, 메모리)가 아니라 **사용자가 체감하는 출력 지표**여야 한다. 예: "초당 주문 성공 수가 950~1000건", "결제 API p99 < 300ms"([[sli-slo-sla]]의 SLI가 바로 이것).

이게 먼저 있어야 실험이 성립한다. 정상의 기준선이 없으면 장애를 주입해도 "나빠졌다"를 측정할 수 없다. 그냥 "느낌상 괜찮아 보인다"로 끝난다.

### 실험은 가설을 검증하는 것이지, 약점을 찾는 게 아니다

여기가 핵심이다. 카오스 실험의 올바른 문장은 이렇다:

> "결제 서비스 인스턴스 1대가 죽어도, 주문 성공률은 정상 상태(950건/초)를 유지할 것이다."

이건 **반증 가능한 가설**이다. 실험 후 두 가지 결론만 나온다 — 가설이 맞았거나(시스템이 견딤, [[circuit-breaker]]·[[retry-exponential-backoff-jitter]]가 작동), 틀렸거나(정상 상태가 깨짐 → 약점 발견). "약점을 찾으러 막 부순다"와의 차이는, 가설이 있으면 **무엇이 깨지면 안 되는지를 미리 안다**는 것이다. 그래서 실험을 언제 멈춰야 하는지도 안다.

### 폭발 반경(blast radius)을 통제하지 않으면 실험이 아니라 사고다

랜덤 파괴와 통제된 실험을 가르는 결정적 선이 **폭발 반경**이다. 잘 설계된 실험은 영향 범위를 처음부터 좁게 가둔다:

- 전체 트래픽이 아니라 **1%**에만 주입한다.
- 모든 인스턴스가 아니라 **단일 AZ / 단일 노드**에만.
- 그리고 **자동 중단(abort) 조건**을 건다 — "주문 성공률이 800건/초 밑으로 떨어지면 즉시 실험 롤백."

이 자동 중단이 없으면 그건 카오스 엔지니어링이 아니라 그냥 장애를 켜둔 것이다. 실험은 "최악이어도 여기까지"라는 천장이 있어야 실험이다.

### 왜 스테이징이 아니라 프로덕션인가

"위험하게 프로덕션에서 왜?"라는 반문이 나온다. 이유는 명확하다 — **스테이징은 프로덕션의 실제 트래픽 패턴, 데이터 규모, 의존성 그래프를 재현하지 못한다.** 커넥션 풀 고갈, 캐시 미스 폭증, 리트라이 폭풍([[retry-exponential-backoff-jitter]]의 thundering herd)은 진짜 부하에서만 나타난다. 다만 프로덕션에서 한다는 건 "막 한다"가 아니라 **위의 폭발 반경 통제가 전제될 때만** 정당화된다.

## 현장 시나리오

한 이커머스가 "결제 서비스는 인스턴스 1대 죽어도 견딘다"고 믿고 있었다. [[circuit-breaker]]도 붙였고, 헬스체크도 있었다. 그래서 작은 카오스 실험을 설계했다.

- **정상 상태 정의**: 주문 성공률 980건/초, 결제 p99 250ms.
- **가설**: 결제 인스턴스 3대 중 1대를 죽여도 정상 상태 유지.
- **폭발 반경**: 카나리아 트래픽 5%만, 자동 중단선은 성공률 850건/초.
- 인스턴스 1대 종료 주입 → 로드밸런서가 헬스체크 실패를 감지하는 데 **30초**가 걸렸다.
- 그 30초 동안 죽은 인스턴스로 보낸 요청이 클라이언트 타임아웃(2초) 후 전부 리트라이 → 살아있는 2대에 1.5배 부하 → 커넥션 풀([[bulkhead-pattern]] 없이 공유 풀) 고갈.
- 주문 성공률이 840건/초로 추락 → **자동 중단 조건 발동 → 실험 즉시 롤백.**
- 사용자 영향은 5% 트래픽에서 약 40초간 지연. 전면 장애는 없었다.

발견된 진짜 약점: 헬스체크 주기가 너무 길고(`interval 10s × 3회 = 30초`), 공유 커넥션 풀이 단일 장애점이었다. 원인 한 줄: **"1대는 견딘다고 믿었지만, 견디는 데 30초가 걸린다는 걸 아무도 측정 안 했다."** 이걸 진짜 장애로 배웠다면 5%가 아니라 100%가 무너졌을 것이다.

## 실무 적용 포인트

1. **정상 상태를 먼저 숫자로 박아라**: 내부 지표(CPU) 말고 사용자 출력 지표(주문 성공률, p99). [[sli-slo-sla]]의 SLI를 그대로 실험 판정 기준으로 쓴다.
2. **모든 실험에 자동 중단(abort) 조건 필수**: "지표가 X 밑이면 즉시 롤백." 이게 없으면 실험을 시작하지 마라. 폭발 반경의 천장이다.
3. **폭발 반경은 1~5%에서 시작**: 트래픽·인스턴스·AZ 단위로 좁게. 성공하면 단계적으로 키운다(`1% → 10% → 50%`). 처음부터 100%는 실험이 아니라 도박.
4. **게임 데이(Game Day)로 운영**: 분기 1회, 관련 팀 모두 모인 자리에서 의도적으로. 모니터링·온콜·롤백 절차까지 함께 점검한다. 발견된 약점은 [[blameless-postmortem]]으로 기록.
5. **주입은 다양하게**: 인스턴스 종료만이 카오스가 아니다. 네트워크 지연(`tc qdisc`로 100ms 추가), 패킷 손실, 의존 서비스 5xx, 디스크 풀, 시계 오차까지. 실제 장애의 형태를 흉내 내라.
6. **[[error-budget]]이 있을 때만 실험**: 이미 SLO를 다 까먹은 상태면 카오스를 돌리지 마라. 남은 에러 버짓 안에서만 의도적 위험을 감수한다.
7. **도구는 통제 기능으로 골라라**: Chaos Monkey(인스턴스 종료), Gremlin·LitmusChaos(주입 유형 다양 + 자동 중단 내장), AWS FIS(폭발 반경/중단 조건 1급 지원). "랜덤하게 죽이는" 기능보다 "안전하게 멈추는" 기능이 더 중요하다.
