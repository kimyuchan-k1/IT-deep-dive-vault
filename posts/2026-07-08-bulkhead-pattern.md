# 결제 API 하나가 느려졌을 뿐인데, 상품 조회도 로그인도 전부 같이 죽었다

## 흔한 오해

"의존성마다 타임아웃이랑 서킷 브레이커만 걸어두면 되잖아. 결제 서비스가 느려지면 그 호출만 타임아웃 나고, 상품 조회나 로그인은 자기 코드 도니까 멀쩡하지."

대부분 그렇게 생각한다. 장애를 호출 단위로 격리한다고 믿는다. 그래서 [[circuit-breaker]] 하나 붙이고 안심한다.

**절반만 맞다.** 타임아웃은 "얼마나 오래 기다릴지"는 정하지만, "그동안 무엇이 점유되는지"는 정하지 못한다. 느린 호출이 타임아웃 3초를 다 채우는 동안, 그 요청을 처리하던 **스레드는 3초 내내 묶여 있다.** 문제는 이 스레드가 결제 전용이 아니라, 상품 조회·로그인이 다 같이 쓰는 **공유 풀**에서 나온다는 것이다.

## 실제 원리

### 서버는 요청마다 스레드를 하나 빌린다

톰캣이든 스프링이든, 들어온 HTTP 요청 하나는 스레드 풀에서 스레드를 하나 꺼내 쓴다. 기본값은 보통 `maxThreads=200` 언저리다. 요청이 끝나야 스레드를 반납한다. 이 풀은 **엔드포인트를 가리지 않는다.** `/pay`든 `/products`든 같은 200개 풀에서 빌린다.

### 느린 의존성은 스레드를 "점유"한다

여기가 핵심이다. 결제 게이트웨이가 응답을 3초씩 끌기 시작한다고 하자. `/pay`로 들어온 요청은 결제 응답을 기다리며 스레드를 3초간 붙잡는다. 초당 100건씩 `/pay`가 들어오면, 3초 안에 300개의 스레드가 필요하다. 그런데 풀은 200개뿐이다.

타임아웃을 3초로 걸어놨어도 소용없다. 타임아웃은 3초 **후에** 스레드를 풀어주지, 그 3초 동안의 점유를 막지 못한다. 서킷 브레이커가 열리기 전까지의 짧은 창에서도, 밀려드는 요청이 순식간에 풀을 바닥낸다.

### 풀이 마르면 무관한 요청도 굶는다

스레드 200개가 전부 결제 대기로 묶이면, 그다음 들어온 `/products` 요청은 **꺼낼 스레드가 없다.** 큐에서 대기하다가 자기도 타임아웃 난다. 상품 조회 코드는 10ms면 끝나는데, 실행할 스레드를 못 받아서 죽는다. 이게 **자원 고갈에 의한 캐스케이드**다. 느린 의존성 하나가 공유 자원을 빨아들여 멀쩡한 기능까지 끌고 내려간다.

### Bulkhead — 배의 격벽에서 온 이름

선박은 선체를 여러 방수 격벽(bulkhead)으로 나눈다. 한 구획에 구멍이 나 물이 차도, 격벽이 막아 배 전체가 가라앉지 않는다. 소프트웨어 Bulkhead도 똑같다. **의존성별로 자원 풀을 쪼갠다.** 결제 호출은 결제 전용 풀(예: 스레드 20개)에서만, 상품 조회는 조회 전용 풀에서만 빌리게 한다. 결제 풀이 다 차면 결제 요청만 거부(fail-fast)되고, 조회는 자기 풀이 멀쩡하니 계속 산다. 침수를 한 구획에 가둔 것이다.

## 현장 시나리오

한 커머스 백엔드는 단일 API 서버에 `/pay`, `/products`, `/login`을 다 태우고 있었다. 톰캣 `maxThreads=200`, 각 외부 호출에 타임아웃 3초 + 서킷 브레이커. "격리는 됐다"고 믿었다.

어느 날 외부 PG사(결제 대행) 지연이 터졌다. 평소 80ms 응답이 2.8초로 늘었다. `/pay`는 초당 120건. 요청들이 PG 응답을 기다리며 스레드를 하나씩 붙잡았고, **1.7초 만에 200개 풀이 전부 결제 대기로 찼다.**

그 순간부터 `/products`와 `/login` 요청은 스레드를 못 받고 큐에서 굶다 타임아웃. p99 레이턴시가 전 엔드포인트에서 폭발했다. 대시보드엔 "결제만 느림"이 아니라 "전 서비스 다운"이 찍혔다. 정작 PG 지연은 결제 트래픽에만 영향을 줬어야 했다.

인과 사슬: PG 응답 80ms→2.8초 → `/pay` 요청이 스레드 장기 점유 → 1.7초 만에 공유 풀 200개 고갈 → `/products`·`/login`이 스레드 못 받음 → 무관한 기능까지 전멸. 수정은 결제 호출을 **전용 Bulkhead(스레드 25개)**로 격리한 것. 다음 PG 지연 때는 결제만 25개 한도에서 fail-fast 났고, 조회·로그인은 [[percentile-p99]]가 평소와 똑같았다.

## 실무 적용 포인트

1. **의존성별로 풀을 쪼갠다.** resilience4j `Bulkhead`나 Hystrix thread-pool isolation으로 외부 호출마다 별도 풀 지정. 전체 스레드가 200이면 결제 25, 검색 25처럼 나눠 한 곳의 고갈이 전체로 안 번지게 한다.
2. **동기 호출엔 Semaphore Bulkhead가 싸다.** 스레드 풀을 통째로 새로 만들면 컨텍스트 스위칭·메모리 비용이 붙는다. resilience4j `SemaphoreBulkhead`는 동시 실행 카운터만 세서 오버헤드가 거의 없다. `maxConcurrentCalls`를 의존성 SLA 기준으로 잡는다.
3. **풀 크기는 리틀의 법칙으로 역산한다.** 필요 동시성 ≈ 초당요청수 × 평균응답시간. `/pay`가 초당 120건에 정상 응답 0.1초면 동시성 12 → 여유 2배 잡아 25. 감이 아니라 [[connection-pool-sizing]]과 같은 공식으로 정한다.
4. **fail-fast를 예외로 잡아 폴백한다.** 풀이 차면 `BulkheadFullException`이 즉시 난다. 이걸 500으로 흘리지 말고, "잠시 후 다시 시도" 응답이나 캐시된 값으로 폴백. 빠른 실패가 느린 성공보다 시스템엔 낫다.
5. **Bulkhead·타임아웃·서킷 브레이커는 세트로 건다.** Bulkhead는 자원 격리, 타임아웃은 점유 시간 상한, [[circuit-breaker]]는 반복 실패 차단. 셋이 다른 축을 막는다. 하나만으로는 이번 같은 고갈을 못 막는다.
6. **격벽 단위로 메트릭을 본다.** 풀별 `available_concurrent_calls`를 대시보드에 띄운다. 특정 Bulkhead만 0에 붙으면 그 의존성만 아픈 것 — 전체 스레드 사용률 하나만 보면 어느 구획이 침수됐는지 못 본다. [[sli-slo-sla]]도 엔드포인트별로 쪼개 본다.
