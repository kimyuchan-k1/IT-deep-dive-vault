# 파이프라인으로 묶었으니 원자적이겠지 — 그 사이로 남의 명령이 끼어든다

## 흔한 오해

> "명령을 파이프라인으로 한 번에 보내면 서버가 그걸 하나의 덩어리로 처리하니까, 중간에 다른 클라이언트가 끼어들 수 없다."

파이프라인을 "묶어서 보낸다"로 이해하면 자연스럽게 따라오는 결론이다. 한 번에 보냈으니 한 번에 처리되겠지. 그래서 재고 차감이나 카운터 갱신 같은 코드가 파이프라인 안에 들어가 있는 걸 심심찮게 본다.

반대편에는 또 다른 오해가 있다. "`MULTI`/`EXEC`은 트랜잭션이니까 RDB처럼 중간에 실패하면 롤백된다." 이것도 틀렸다. Redis의 트랜잭션에는 **롤백이 아예 없다**.

두 오해가 같은 뿌리에서 나온다. 파이프라이닝과 트랜잭션을 같은 축 위에 놓고 "약한 버전 / 강한 버전"으로 생각하는 것이다. 둘은 애초에 다른 축이다.

## 실제 원리

파이프라이닝은 **네트워크 계층**의 최적화고, `MULTI`/`EXEC`은 **실행 계층**의 격리다. 겹치는 부분이 없다.

**파이프라이닝: RTT를 접는 것**

일반적인 요청은 명령 하나당 왕복 1회다. 명령 N개면 N × RTT. RTT가 1ms인 환경에서 1000개 명령은 그것만으로 1초다. 실제 Redis가 명령 하나 처리하는 데 쓰는 시간은 마이크로초 단위이므로, 이 1초는 전부 대기 시간이다.

파이프라이닝은 응답을 기다리지 않고 소켓에 명령을 연달아 밀어넣는다. 서버는 도착한 순서대로 처리하고 응답을 버퍼에 쌓아 돌려준다. N × RTT가 대략 1 × RTT로 접힌다.

여기서 서버가 하는 일을 정확히 보자. 서버는 소켓에서 읽은 명령을 **하나씩 순서대로** 실행할 뿐이다. 파이프라인이라는 개념 자체가 서버에는 없다. 서버 입장에서는 그냥 한 클라이언트가 명령을 빨리 보낸 것이다. 이벤트 루프는 여러 클라이언트의 소켓을 번갈아 처리하므로, 내 3번 명령과 4번 명령 사이에 **다른 클라이언트의 명령이 실행될 수 있다**. 원자성이 없는 게 아니라, 원자성을 제공한다고 말한 적이 없다.

```
클라이언트 A 파이프라인: [GET stock] [SET stock 9]
서버 실행 순서:  GET stock(A) → INCR stock(B) → SET stock 9(A)
                                   ↑ B가 끼어듦. A의 SET이 B를 덮어씀
```

**MULTI/EXEC: 큐잉 후 한 번에 실행**

`MULTI` 이후의 명령은 즉시 실행되지 않는다. 서버가 해당 클라이언트의 큐에 쌓아두고 `QUEUED`만 응답한다. `EXEC`이 오면 그때 큐 전체를 **단일 이벤트 루프 사이클 안에서** 연속 실행한다. Redis의 명령 실행은 단일 스레드이므로, 이 구간에는 다른 클라이언트의 명령이 절대 끼어들지 못한다. 원자성의 근거는 "트랜잭션 매니저"가 아니라 [[redis-single-thread]] 그 자체다.

**롤백이 없다는 것의 의미**

에러는 두 시점에 발생한다.

*큐잉 시점 에러* — 존재하지 않는 명령, 인자 개수 불일치처럼 파싱 단계에서 잡히는 것. 이건 큐에 들어갈 때 거부되고, 이후 `EXEC`은 `EXECABORT`로 전체를 실행하지 않는다.

*실행 시점 에러* — `WRONGTYPE`처럼 실제 실행해봐야 아는 것. 이건 **그 명령만 에러를 반환하고 나머지는 전부 정상 커밋된다**. 3개 중 2번째가 실패해도 1번과 3번은 반영된다. 되돌릴 방법은 없다.

Redis가 이렇게 설계한 이유는 명확하다. 실행 시점 에러는 대부분 프로그래밍 오류이고, 롤백 장치를 넣으면 모든 명령에 상시 비용이 붙는다. 성능을 지키기 위해 안전망을 뺀 트레이드오프다.

**WATCH: 없는 격리를 메우는 장치**

`MULTI`/`EXEC`은 읽고-판단하고-쓰는 패턴을 못 한다. 큐잉 중에는 `GET`의 결과를 볼 수 없기 때문이다. 그래서 `WATCH key`가 있다. `WATCH` 이후 `EXEC` 전까지 해당 키가 변경되면 `EXEC`은 전체를 취소하고 `nil`을 반환한다. 낙관적 락(CAS)이고, 실패하면 애플리케이션이 재시도해야 한다. 이건 [[optimistic-locking]]의 교과서적 구현이다.

## 현장 시나리오

한 이커머스의 쿠폰 발급 API. 선착순 1000장이고, 트래픽이 몰릴 때를 대비해 개발자가 Redis 호출을 파이프라인으로 묶어 최적화했다.

```
파이프라인: [GET coupon:count] → [INCR coupon:count] → [SADD coupon:users {uid}]
```

응답 시간은 3ms에서 1.1ms로 줄었다. 부하 테스트도 통과했다. 문제는 초당 요청이 200을 넘기면서 나타났다.

`GET`으로 998을 읽은 요청 A가 조건 검사를 하는 사이, 서버 이벤트 루프는 다른 클라이언트 B, C의 `INCR`을 처리했다. A가 `INCR`을 실행할 때 카운터는 이미 1000이었다. A뿐 아니라 같은 순간에 998~999를 읽은 요청 수십 개가 전부 "아직 여유 있음"으로 판단했다.

발급된 쿠폰은 1,047장. 재무팀이 정산에서 47장의 초과분을 발견하기까지 사흘이 걸렸다. 파이프라인은 정확히 설계된 대로 동작했다. RTT를 줄였을 뿐, 아무것도 보호하지 않았다.

## 실무 적용 포인트

1. **읽고-판단-쓰기가 있으면 파이프라인이 아니라 Lua다.** `EVAL`로 보낸 스크립트는 서버에서 원자적으로 실행되고, 중간 값을 스크립트 안에서 쓸 수 있다. 위 쿠폰 로직은 `EVAL "local c = redis.call('GET', KEYS[1]) ..."` 한 방이면 끝난다. [[redis-lua-script]] 참고.

2. **`WATCH` + 재시도는 경합이 낮을 때만.** 실패 시 전체 재시도이므로, 같은 키에 초당 수백 건이 몰리면 재시도 폭풍이 된다. 재시도 상한을 3회 정도로 두고, 초과하면 Lua나 큐로 우회한다.

3. **파이프라인 배치 크기는 100~1000개.** 무한정 밀어넣으면 서버 출력 버퍼가 부풀어 메모리를 먹는다. `client-output-buffer-limit normal 0 0 0`은 일반 클라이언트에 제한이 없다는 뜻이므로, 대량 파이프라인을 쓴다면 배치를 애플리케이션 쪽에서 끊는 게 안전하다.

4. **Cluster에서는 키가 같은 슬롯에 있어야 한다.** `MULTI`/`EXEC`과 Lua 모두 여러 슬롯에 걸치면 `CROSSSLOT` 에러다. 해시태그로 묶는다: `coupon:{event123}:count`, `coupon:{event123}:users`.

5. **`MULTI` 안에 무거운 명령을 넣지 않는다.** `EXEC` 구간 전체가 단일 스레드를 점유한다. 큐에 `KEYS *`나 대용량 `SMEMBERS`가 하나 있으면 그동안 전체 서버가 멈춘다. `SLOWLOG GET`으로 `EXEC` 항목이 잡히는지 주기적으로 확인한다.

6. **에러 응답을 버리지 않는다.** 파이프라인이든 `EXEC`이든 응답은 배열로 온다. 다수 클라이언트 라이브러리가 개별 에러를 조용히 통과시키므로, 배열 각 원소의 타입을 검사하는 코드를 넣는다.
