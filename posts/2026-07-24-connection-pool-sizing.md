# 커넥션 풀을 100으로 키웠더니 오히려 느려졌다

트래픽이 몰리면서 응답이 느려졌다. 스레드 덤프를 보니 커넥션 풀 대기가 잔뜩 걸려 있다. 그래서 풀 사이즈를 20에서 100으로 올렸다. 결과는 반대였다. p99가 더 나빠지고, DB CPU는 100%에 붙었다. 대기를 없애려고 넣은 숫자가 병목을 DB 안으로 밀어 넣었을 뿐이다.

## 흔한 오해

> "커넥션이 부족해서 대기가 걸리니까, 풀을 크게 잡으면 그만큼 동시에 처리되겠지."

풀 사이즈를 **동시 처리 가능 개수**로 이해하는 통념이다. 100개 커넥션 = 쿼리 100개 병렬 실행이라고 그림을 그린다. 대기 큐가 길면 큐를 없애는 방향, 즉 커넥션을 늘리는 방향으로 손이 간다.

틀린 건 아니다. 커넥션이 하나뿐이면 당연히 직렬화된다. 다만 "많을수록 좋다"는 방향이 어느 지점에서 뒤집힌다는 걸 빠뜨렸다. 커넥션은 공짜 자원이 아니라 **DB 서버의 물리 코어를 두고 경쟁하는 스레드**다.

## 실제 원리

### 커넥션 100개라도 진짜 병렬은 코어 수만큼

DB가 쿼리를 실제로 "실행"하는 건 CPU 코어다. 8코어 서버라면 어느 순간이든 CPU 위에서 도는 쿼리는 최대 8개다. 커넥션 100개가 동시에 바쁘면, 92개는 실행 중이 아니라 **런큐에서 순서를 기다리거나 컨텍스트 스위칭 비용을 만들고 있다**.

여기가 핵심이다. 커넥션을 늘려도 총 처리 능력(코어)은 그대로다. 늘어나는 건 경쟁하는 참가자 수뿐이다. 참가자가 많아지면 스케줄러 오버헤드, 캐시 오염, 락 경합이 커진다. 그래서 어느 지점을 넘으면 처리량이 **떨어진다**. 이게 100으로 키웠더니 느려진 이유다.

### 대기 시간의 진짜 계산: Little's Law

풀 사이즈는 감이 아니라 공식으로 잡는다. 대기행렬 이론의 Little's Law:

```
동시 진행 중인 요청 수(L) = 도착률(λ) × 처리 시간(W)
```

초당 500 쿼리가 들어오고(λ=500), 쿼리 하나가 평균 10ms 걸린다면(W=0.01s):

```
L = 500 × 0.01 = 5
```

**필요한 커넥션은 5개**다. 100이 아니다. 트래픽이 두 배로 튀는 순간을 감안해 여유를 줘도 10~15면 충분하다. 100은 90% 이상이 놀거나, 놀지 않는다면 DB를 질식시킨다는 뜻이다.

### HikariCP가 권하는 시작 공식

HikariCP 위키의 유명한 출발점:

```
pool size = (코어 수 × 2) + 유효 스핀들 수
```

8코어 + SSD/디스크 1축이면 `8×2+1 = 17`. 오래된 경험칙이지만 방향은 Little's Law와 같다. **수십이지 수백이 아니다.** 코어 × 2인 이유는, 쿼리가 항상 CPU만 쓰는 게 아니라 디스크 I/O나 네트워크로 잠깐 블로킹되는 틈에 다른 커넥션이 코어를 쓰기 때문이다. 그 틈을 메우는 여유가 "×2"다.

## 현장 시나리오

주문 API 서버 10대. 각 서버 커넥션 풀 20개. 평소 DB(16코어) CPU 40%로 평온. 프로모션이 터지고 대기가 관측됐다. 팀은 각 서버 풀을 20에서 100으로 올렸다.

- 서버 10대 × 100 = 커넥션 **1,000개**가 16코어 DB로 몰림
- 1,000개 중 실제 실행 16개, 나머지 984개는 런큐 대기 + 컨텍스트 스위칭
- 커넥션당 work_mem·정렬 버퍼가 붙어 **DB 메모리 압박**, 스왑 발생
- 쿼리 하나 처리 시간이 10ms에서 40ms로 늘어남 → Little's Law상 필요 커넥션이 더 커지는 악순환
- p99 120ms → 900ms, DB CPU 100% 고정, 처리량은 오히려 하락

롤백은 반대 방향이었다. 서버당 풀을 **10으로 줄였다**. 총 100 커넥션. 대기 큐는 생기지만 큐에서 기다리는 시간이 DB에서 뒤엉키는 시간보다 짧았다. p99가 다시 세 자리로 내려왔다. 원인 한 줄: "코어는 16개인데 손님을 1,000명 들였다."

## 실무 적용 포인트

1. **Little's Law로 상한을 먼저 계산**: `L = λ × W`. 피크 도착률 × 평균 쿼리 시간. 이게 필요 커넥션의 이론값이다.
2. **전체 합산으로 본다**: 앱 서버 N대면 DB가 받는 건 `N × 서버당 풀`. 서버당 20이 작아 보여도 서버 50대면 1,000이다. DB `max_connections`와 코어 수 기준으로 역산해라.
3. **HikariCP `maximumPoolSize`는 수십 단위에서 시작**: `(코어×2)+스핀들`로 잡고 부하 테스트로 미세 조정. 기본값 10을 함부로 100으로 올리지 마라.
4. **대기는 `connectionTimeout`으로 빠르게 실패시킨다**: HikariCP 기본 30s는 너무 길다. 250ms~2s로 잡아 [[backpressure-patterns]]처럼 빨리 튕겨내는 게 큐를 무한정 쌓는 것보다 낫다.
5. **풀을 용도별로 쪼갠다**: 짧은 OLTP 쿼리 풀과 무거운 리포트 쿼리 풀을 분리. [[bulkhead-pattern]]으로 느린 쿼리가 빠른 쿼리 커넥션을 잠식하지 못하게.
6. **DB쪽 상한도 같이 본다**: Postgres는 커넥션당 프로세스 + work_mem이 붙는다. 수백 커넥션이 필요하면 풀을 키우지 말고 PgBouncer 같은 [[connection-pool-timeout]] 계열 외부 풀러를 앞에 둬라.

## 더 깊은 토끼굴

커넥션 풀은 "동시성을 늘리는 장치"가 아니라 **유한한 DB 코어로 들어가는 요청을 조절하는 밸브**다. 밸브를 활짝 열면 물이 더 흐르는 게 아니라 파이프가 터진다. 처리량은 코어가 정하고, 풀은 그 코어를 넘지 않게 막는 역할이다.

- [[replication-lag]] — 읽기를 레플리카로 분산할 때의 함정
