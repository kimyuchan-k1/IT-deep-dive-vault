# 매일 백업이 돌고 있었는데, 복구해보니 3시간치가 사라졌다

백업은 매일 새벽 4시에 돌았다. 실패 알람도 없었다. 오전 7시에 사고가 났고, 팀은 "최대 3시간치만 날리면 된다"고 계산했다. 실제로 복구를 끝내고 보니 정확히 3시간치가 통째로 없었다. 계산이 맞은 게 아니라, 복구할 수 있는 지점이 새벽 4시 하나뿐이었던 것이다.

## 흔한 오해

> "백업이 매일 돌면 최악이 하루치잖아. WAL은 그냥 성능용 로그 아니야?"

WAL(Write-Ahead Log)을 성능 최적화 장치로 배우는 경우가 많다. 랜덤 쓰기를 순차 쓰기로 바꿔서 빠르다, 커밋할 때 데이터 파일 대신 로그만 fsync하니까 빠르다 — 다 맞는 설명이다. 그래서 WAL은 "DB 내부 사정"이고 백업은 "운영 사정"으로 분리해서 생각하게 된다.

여기서 어긋난다. WAL은 성능 장치이기도 하지만, **백업과 백업 사이의 시간을 복구 가능하게 만드는 유일한 재료**다. WAL을 따로 보관하지 않으면 복구 가능 지점은 백업을 뜬 그 순간들뿐이다. RPO는 백업 주기가 아니라 WAL 보관 주기가 결정한다.

## 실제 원리

### 데이터 파일보다 로그가 먼저 간다

트랜잭션이 커밋될 때 DB가 하는 일은 변경된 8KB 페이지들을 디스크에 쓰는 게 아니다. "이 페이지의 이 오프셋을 이렇게 바꿨다"는 변경 기록을 WAL 파일 끝에 순차로 붙이고, 그것만 fsync한다. 실제 데이터 파일 반영은 나중에 백그라운드로 밀린다.

이게 write-ahead 규칙이다. 더티 페이지를 디스크에 내리기 전에 그 페이지를 설명하는 WAL 레코드가 먼저 안전하게 저장돼 있어야 한다. 순서가 뒤집히면 크래시 후 "데이터 파일은 바뀌었는데 왜 바뀌었는지 모르는" 상태가 되고, 그건 복구가 불가능한 상태다.

각 WAL 레코드에는 LSN(Log Sequence Number)이 붙는다. 로그 스트림 안의 바이트 오프셋이고, 모든 데이터 페이지 헤더에도 "이 페이지에 마지막으로 반영된 LSN"이 박혀 있다. 크래시 후 복구는 이 두 LSN을 비교하며 진행된다. 페이지의 LSN보다 큰 WAL 레코드만 다시 적용(redo)하면 된다.

### 체크포인트는 복구 시작점을 앞으로 당기는 일

체크포인트는 그 시점까지의 더티 페이지를 전부 디스크에 내리고, "여기부터 redo 시작하면 됨"이라는 지점(redo point)을 제어 파일에 기록한다. 체크포인트가 뜸하면 WAL이 길게 쌓이고 크래시 복구가 오래 걸린다. 잦으면 I/O가 튄다. PostgreSQL의 `checkpoint_timeout`(기본 5분)과 `max_wal_size`(기본 1GB)가 이 균형을 잡는 손잡이다.

### base backup은 그 자체로는 깨진 스냅샷이다

여기가 핵심이다. `pg_basebackup`이 데이터 디렉토리를 복사하는 동안에도 DB는 계속 쓰고 있다. 복사 초반에 읽은 파일과 후반에 읽은 파일은 서로 다른 시점을 보고 있다. 즉 **base backup 자체는 일관성이 깨진 상태**다.

그럼 어떻게 복구되나. 백업 시작 시점의 WAL 위치부터, 백업 종료 시점의 WAL 위치까지를 그 스냅샷 위에 redo로 다시 적용한다. 그제서야 처음으로 일관된 상태가 된다. 백업이 WAL 없이는 애초에 복원조차 안 된다는 뜻이다.

그리고 이 redo를 백업 종료 시점에서 멈추지 않고 계속 밀면, 그게 PITR(Point-In-Time Recovery)이다. 원하는 지점에서 멈추라고 지정하는 게 `recovery_target_time` / `recovery_target_lsn` / `recovery_target_xid`다. 복구 후에는 새 timeline이 생기고, 갈라진 이력은 `.history` 파일로 아카이브에 남는다.

정리하면 복구 가능 시점의 집합은 이렇게 결정된다.

```
복구 가능 구간 = [base backup 종료 LSN, 아카이브된 마지막 WAL의 LSN]
```

base backup만 있고 WAL 아카이브가 비어 있으면 이 구간은 점 하나로 붕괴한다. 그 점이 새벽 4시였다.

## 현장 시나리오

이커머스 주문 DB, PostgreSQL 15. 구성은 이랬다.

- 새벽 4시 `pg_basebackup` → S3 업로드 (성공 알람까지 있었음)
- `archive_mode = on`, `archive_command = 'cp %p /mnt/wal_archive/%f'`
- `/mnt/wal_archive`는 별도 NFS 볼륨 — 이라고 문서에 적혀 있었다

3주 전 인스턴스 재부팅이 있었고, `/etc/fstab`에 그 NFS 마운트가 빠져 있었다. 마운트는 안 붙었고, `/mnt/wal_archive` 디렉토리는 로컬 루트 디스크에 그대로 남아 있었다. `cp`는 아무 불평 없이 로컬 디렉토리에 파일을 썼다. **exit code 0.** PostgreSQL 입장에서 아카이빙은 3주 내내 성공이었다. `pg_stat_archiver`의 `failed_count`도 0이었다.

오전 7시 12분, 배포된 마이그레이션이 `orders` 테이블의 `status` 컬럼을 통째로 덮어썼다. 7시 20분 롤백 결정, 7시 25분 PITR 시도 — `recovery_target_time = '2026-07-28 07:10:00'`.

그런데 그 시점의 WAL 세그먼트를 가져올 곳이 없었다. 아카이브는 죽은 인스턴스의 로컬 디스크에 있었고, 그 인스턴스는 복구를 위해 이미 재프로비저닝된 뒤였다. 남은 건 S3의 새벽 4시 base backup 하나. 4시로 복구했고, 4시~7시 12분 사이의 주문 3만 1천 건은 애플리케이션 로그를 긁어서 손으로 채워 넣었다.

원인 한 줄: `cp`가 성공했다는 말은 파일이 안전한 곳에 있다는 뜻이 아니었다.

## 실무 적용 포인트

1. **`archive_command`는 "다른 물리 저장소에 도착했을 때만" 0을 반환해야 한다.** `cp %p /mnt/...`는 마운트가 빠져도 성공한다. 최소한 `test ! -f /mnt/wal_archive/%f && cp %p /mnt/wal_archive/%f`로 덮어쓰기를 막고, 실제로는 `pgbackrest`나 `wal-g` 같은 도구로 오브젝트 스토리지에 직접 올려라. 검증 없는 `cp`는 아카이빙이 아니라 복사다.

2. **`pg_stat_archiver`를 모니터링하되, `failed_count`만 보지 마라.** `archived_count`가 일정 시간 동안 안 늘어나는 것, 그리고 `last_archived_time`이 현재 시각과 벌어지는 것을 함께 본다. 위 사고에서 `failed_count`는 끝까지 0이었다. 아카이브 저장소 쪽에서 파일 개수를 세는 역방향 체크가 진짜 감시다.

3. **RPO는 `archive_timeout`으로 정한다.** WAL 세그먼트는 기본 16MB가 다 차야 아카이브된다. 트래픽이 적은 시간대엔 한 세그먼트가 몇 시간을 안 넘어가기도 한다. `archive_timeout = 60`이면 최소 60초마다 강제로 세그먼트를 닫아 RPO 60초를 만든다. 대신 매번 16MB 파일이 생기니 저장 비용과 맞바꾸는 값이다.

4. **replication slot은 pg_wal을 무한정 채울 수 있다.** 죽은 스탠바이의 슬롯이 살아 있으면 PostgreSQL은 그 슬롯이 소비할 때까지 WAL을 지우지 않는다. 디스크가 차면 DB가 PANIC으로 멈춘다. `max_slot_wal_keep_size = 100GB` 같은 상한을 반드시 걸고, `pg_replication_slots`의 안 쓰는 슬롯을 정기적으로 지워라.

5. **복구 훈련을 일정에 넣어라.** 분기 1회, 실제 아카이브에서 임의 시점으로 복원해보고 소요 시간을 잰다. `recovery_target_action = 'pause'`로 멈춰 세워 데이터를 확인한 뒤 `pg_wal_replay_resume()`으로 진행하면 안전하다. 복원해본 적 없는 백업은 백업이 아니라 파일이다.

6. **백업 무결성은 `pg_verifybackup`으로 검증한다.** `pg_basebackup`이 남기는 `backup_manifest`와 대조해 파일 누락·체크섬 불일치를 잡는다. 업로드 파이프라인 중간에서 잘린 백업은 복구를 시작해봐야 알게 된다.

## 더 깊은 토끼굴

WAL redo가 "페이지 LSN보다 큰 레코드만 다시 적용"하는 구조는 [[mvcc-how]]에서 튜플 가시성을 판단하는 방식과 짝을 이룬다. 복구된 시점의 스냅샷이 무엇을 보는지는 결국 두 메커니즘이 같이 결정한다. 순차 로그에 먼저 쓰고 나중에 정리하는 발상 자체는 [[lsm-tree-rocksdb]]의 memtable/SSTable 구조와 뿌리가 같다. 스탠바이가 WAL을 얼마나 늦게 따라오는지는 [[replication-lag]]에서, 이번 같은 사고를 어떻게 기록해 남기는지는 [[blameless-postmortem]]에서 이어진다. redo가 건드리는 페이지 구조 자체는 [[btree-index-internals]]에 있다.
