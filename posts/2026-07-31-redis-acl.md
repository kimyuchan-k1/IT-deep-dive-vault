# 테넌트마다 ACL을 걸었는데 한 테넌트가 남의 세션을 다 날렸다

새벽 2시, 로그인 세션이 통째로 날아갔다는 문의가 여러 고객사에서 동시에 들어왔다. Redis는 살아 있었다. 에러 로그도 없었다. 각 테넌트는 자기 키 접두사 밖으로 나갈 수 없게 ACL이 걸려 있었고, 그 설정은 그날도 정확히 동작했다. 문제는 ACL이 동작하지 않은 게 아니라, ACL이 애초에 그 문제를 다루는 물건이 아니었다는 데 있었다.

## 흔한 오해

> "Redis 6부터 ACL이 생겼으니 테넌트별로 유저 만들고 `~tenant:{id}:*`로 키 패턴 묶으면 한 인스턴스에 여러 고객을 태워도 되잖아."

`requirepass` 비밀번호 하나로 전부를 여닫던 시절을 생각하면 큰 진전인 건 맞다. `rename-command`로 `FLUSHALL`을 숨기는 임시방편도 이제 필요 없다. 유저별로 명령과 키를 나눌 수 있으니 논리적으로도 깔끔해 보인다.

여기까지는 맞다. 어긋나는 지점은 **"내 키만 만질 수 있다"를 "내 테넌트가 격리됐다"로 읽는 순간**이다. ACL은 인가(authorization) 계층이다. 자원(resource) 계층은 손대지 않는다. 이 둘의 경계가 어디인지 모르면, 권한은 완벽한데 장애는 전부 옆 테넌트에서 넘어온다.

## 실제 원리

### ACL이 실제로 검사하는 세 가지

명령이 들어오면 Redis는 세 가지를 본다. 명령 자체가 허용됐는가(`+@read`, `-flushall`), 인자로 들어온 키가 패턴에 걸리는가(`~app:*`), pub/sub 채널이 허용됐는가(`&notify:*`). 규칙은 **왼쪽에서 오른쪽으로 순차 적용**되고 뒤가 앞을 덮는다. 그래서 `+@all -@dangerous`는 "전부 주고 위험한 것만 회수"이고, 순서를 뒤집으면 의미가 사라진다.

```
ACL SETUSER t42 on >pw ~t:42:* &t:42:* +@all -@dangerous -@admin
```

또 하나 자주 걸리는 성질: `ACL SETUSER`는 **누적**이다. 기존 유저에 같은 명령을 다시 쓰면 규칙이 교체되는 게 아니라 합쳐진다. 권한을 좁히려면 앞에 `reset`을 붙여 초기화하고 다시 쌓아야 한다. Redis 7부터는 여기에 읽기/쓰기 분리(`%R~cache:*`는 읽기만, `%W~`는 쓰기만)와 selector(`(+get ~public:*)` 같은 추가 권한 묶음)가 붙었다.

### 검사 목록에 없는 것

목록에 없는 것을 보면 경계가 드러난다. **메모리 사용량, 명령 실행 시간, 커넥션 수, 초당 요청 수 — ACL은 이 중 아무것도 세지 않는다.** Redis에는 유저별 메모리 쿼터도, 유저별 rate limit도 없다.

그래서 다음 두 개가 그대로 공유 자원으로 남는다.

첫째, `maxmemory`와 eviction 정책은 **인스턴스 전역**이다. `allkeys-lru`가 걸려 있으면 축출 대상은 전체 키스페이스에서 골라진다. 어느 테넌트가 채웠는지, 어느 테넌트 키를 버리는지는 고려 대상이 아니다. 한 테넌트가 메모리를 밀어 올리면 대가는 **가장 덜 최근에 접근된 키**를 가진 쪽이 치른다. 세션처럼 TTL은 길고 접근은 뜸한 키가 정확히 그 조건이다.

둘째, Redis는 명령 실행이 싱글 스레드다. 한 테넌트가 자기 패턴 안에서 완벽히 합법적으로 `SMEMBERS`를 큰 집합에 날리면 그동안 전원이 멈춘다. 권한 검사를 통과한 O(N) 명령은 ACL이 막을 수 있는 대상이 아니다. [[redis-bigkey]]에서 본 블로킹이 테넌트 경계를 그대로 무시하고 넘어간다.

### 기본값이 열려 있는 자리

`default` 유저는 설정을 안 건드리면 `on nopass ~* &* +@all`이다. 새 유저를 아무리 촘촘히 짜도 이걸 끄지 않으면 우회로가 그대로 열려 있다.

pub/sub도 함정이 있다. 채널 권한 기본값을 정하는 `acl-pubsub-default`가 Redis 6.x에서는 `allchannels`였다. 키 패턴만 신경 쓰고 `&`를 안 쓴 6.x 설정은 **모든 테넌트가 서로의 채널을 구독할 수 있는 상태**다. Redis 7.0에서 기본값이 `resetchannels`로 바뀌었는데, 이건 6.x 설정 파일을 그대로 들고 7로 올리면 구독이 갑자기 끊긴다는 뜻이기도 하다.

번호 DB(`SELECT 0~15`)도 격리가 아니다. ACL 키 패턴에는 DB 개념이 없어서 모든 DB에 동일하게 적용되고, Cluster 모드에서는 DB 0 하나뿐이다.

## 현장 시나리오

B2B SaaS. Redis 7 단일 인스턴스에 고객사 23곳, `maxmemory 8gb`, `maxmemory-policy allkeys-lru`. 테넌트마다 ACL 유저를 만들고 `~t:{id}:*`로 묶어뒀다. 감사에서도 통과한 구성이었다.

새벽 1시 40분, 고객사 한 곳이 연동 초기 적재 배치를 돌렸다. 상품 카탈로그 210만 건을 캐시에 밀어 넣는 작업이었고, 자기 패턴 안에서만 썼다. 권한 위반 0건, ACL LOG 0건.

메모리가 20분 만에 5.1GB에서 8GB에 닿았다. 여기서부터 LRU가 돌기 시작했다. 방금 적재한 카탈로그 키는 전부 갓 접근된 상태라 축출 후보에서 밀렸다. 대신 다른 22개 고객사의 `t:*:sess:*` 키들이 뽑혔다 — TTL 24시간에 접근은 로그인 시 한 번뿐이라, LRU 관점에서 가장 버리기 좋은 키였다.

세션이 사라지자 앱은 정상 동작으로 로그아웃을 반환했다. 새벽 2시 10분까지 22개 고객사에서 강제 로그아웃 문의가 쌓였다. 원인 테넌트는 자기 배치가 끝난 줄도 몰랐다.

원인 한 줄: 권한 경계는 23개였는데, 메모리 경계는 1개였다.

## 실무 적용 포인트

1. **`default` 유저부터 닫는다.** `ACL SETUSER default off` 또는 설정 파일에 `user default off`. 운영 접속용 유저를 먼저 만들어 검증한 뒤에 끄지 않으면 자기 손을 자른다. ACL은 `aclfile` 경로로 분리하고 `ACL SAVE`/`ACL LOAD`로 관리한다 — `redis.conf`의 `user` 지시자와 `aclfile`은 동시에 못 쓴다.

2. **명령은 카테고리로 빼고 목록으로 확인한다.** `+@all -@dangerous -@admin`을 기본으로 두되, `ACL CAT dangerous`로 실제 무엇이 빠졌는지 눈으로 본다. `KEYS`, `FLUSHALL`, `FLUSHDB`, `CONFIG`, `DEBUG`, `SHUTDOWN`, `SWAPDB`가 여기 들어간다. `CONFIG SET`이 남아 있으면 테넌트가 `maxmemory-policy`를 바꿀 수 있다.

3. **키 패턴에 읽기/쓰기를 분리한다.** Redis 7의 `%R~t:42:shared:*`로 공용 데이터는 읽기만, 자기 네임스페이스는 `~t:42:*`로 전부. 하나의 유저에 성격이 다른 권한이 필요하면 selector `(+@read %R~ref:*)`로 묶어 규칙 하나를 넓히는 대신 묶음을 추가한다.

4. **채널 기본값을 명시한다.** `acl-pubsub-default resetchannels`를 설정 파일에 박아두고 유저마다 `&t:{id}:*`를 준다. 버전 기본값에 기대면 업그레이드 때 조용히 열리거나 조용히 끊긴다.

5. **`ACL LOG`를 지표로 올린다.** 거부 이력이 `reason`(`command`/`key`/`channel`/`auth`), `object`, `username`, `client-info`와 함께 쌓인다. 주기적으로 수집하고 배포 직후 급증을 알람으로 건다 — 권한 누락이 애플리케이션 에러로 위장되는 걸 막는 유일한 창구다. 확인 후 `ACL LOG RESET`.

6. **격리가 필요하면 ACL 밖에서 만든다.** 메모리·CPU 경계는 인스턴스 분리로만 만들어진다. 같이 태워야 한다면 최소한 (a) 세션처럼 잃으면 안 되는 키는 `maxmemory-policy volatile-lru`가 아니라 **전용 인스턴스**로 빼고, (b) `maxmemory-clients`로 클라이언트 출력 버퍼 폭주를 제한하고, (c) 대량 적재는 애플리케이션 쪽에서 속도를 조절한다. [[connection-pool-sizing]]처럼, 한계는 공유 자원 쪽에 걸어야 의미가 있다.

## 더 깊은 토끼굴

ACL은 [[rbac-abac-rebac]]에서 말하는 권한 모델을 데이터 저장소 안으로 끌어들인 것이고, 인증 자체는 여전히 별도 문제다 — 비밀번호를 어떻게 전달하느냐는 [[mtls-zero-trust]] 쪽 이야기다. `+eval`을 주는 순간 권한 표면이 스크립트 본문으로 옮겨가므로, [[redis-lua-atomic]]을 쓴다면 스크립트가 만질 키를 `KEYS`로 선언하게 강제하거나 `@scripting`을 통째로 빼는 편이 낫다. 멀티테넌시를 인스턴스가 아니라 슬롯 단위로 나누는 방향은 [[redis-cluster-slot]]에 이어진다.
