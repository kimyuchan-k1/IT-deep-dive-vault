# DB는 2초 만에 살아났는데 장애는 40분 더 갔다

원인은 이미 사라진 뒤였다. Primary 페일오버는 2.1초 만에 끝났고 새 Primary는 정상이었다. 그런데 주문 API는 그 뒤로 40분을 더 죽어 있었다. 대시보드에는 DB CPU 100%가 계속 찍혔다. 아무도 장애를 일으키고 있지 않았다. 시스템이 스스로를 계속 죽이고 있었다.

## 흔한 오해

> "재시도는 넣어두면 손해 볼 게 없잖아. 실패하면 한 번 더 해보는 건데."

이 인상은 근거가 있다. 네트워크 오류 대부분은 짧고, 한 번 더 보내면 대개 성공한다. HTTP 클라이언트도 SDK도 재시도를 기본값으로 켜둔 채 배포된다. 그래서 "재시도 = 가용성 증가"로 읽힌다.

한 대의 클라이언트만 놓고 보면 맞다. 틀린 건 **"각자 한 번 더"가 전체에도 한 번 더로 끝난다**는 부분이다. 재시도는 실패를 흡수하는 장치가 아니라 **부하를 곱하는 장치**다. 그리고 실패는 보통 한 클라이언트에게만 오지 않는다. 공용 의존성이 흔들리면 전 클라이언트가 **동시에** 실패하고, 동시에 실패한 클라이언트는 **동시에** 재시도한다.

## 실제 원리

### 지수 백오프만으로는 동기화가 안 풀린다

`sleep = base × 2^attempt`. 첫 재시도 100ms, 다음 200ms, 400ms, 800ms. 부하를 시간축에 흩뿌리려는 의도인데, 여기에 함정이 있다.

10,000개 클라이언트가 **같은 순간** 실패했다고 하자. 이들은 전부 같은 수식으로 같은 값을 계산한다. 그래서 100ms 뒤에 10,000개가 한꺼번에 다시 온다. 200ms 뒤에 또 한꺼번에. 백오프는 파형의 **간격만 늘렸을 뿐 폭을 전혀 줄이지 못했다**. 서버가 보는 건 완만해진 곡선이 아니라 점점 뜸해지는 스파이크 열이다.

여기가 핵심이다. 백오프가 푸는 문제는 "너무 자주 온다"이고, 동시 실패가 만드는 문제는 "**같은 순간에** 온다"다. 두 번째는 랜덤 없이는 안 풀린다.

### 지터의 세 가지 형태

AWS가 2015년 시뮬레이션으로 정리한 세 가지가 사실상 표준이다.

```
temp = min(cap, base * 2^attempt)

Full jitter   : sleep = random(0, temp)
Equal jitter  : sleep = temp/2 + random(0, temp/2)
Decorrelated  : sleep = min(cap, random(base, sleep_prev * 3))
```

Full jitter는 대기 시간을 `[0, temp)` 전체에 균등하게 흩는다. 클라이언트 입장에선 평균 대기가 절반으로 줄어드는 대신 편차가 커지고, **서버 입장에선 순간 최대 동시 요청 수가 가장 크게 줄어든다**. AWS 실험에서 총 호출 수와 완료 시간을 가장 잘 줄인 게 이 방식이다. Equal jitter는 최소 대기를 보장해 개별 요청의 예측 가능성을 조금 사고, 그만큼 분산을 판다.

지터는 재시도만의 이야기가 아니다. 캐시 TTL을 전부 300초로 박으면 같은 이유로 만료가 동기화된다 — [[cache-stampede]]가 그 파형이다. SSE 재연결 대기도, 크론도 마찬가지다. **공용 상수는 곧 동기화 장치다.**

### 진짜 킬러는 계층별 재시도 증폭

지터를 넣어도 남는 문제가 있다. 재시도가 **한 계층에만** 있는 경우는 드물다.

```
게이트웨이(3회) → 주문 서비스(3회) → 재고 서비스(3회) → DB
                                      3 × 3 × 3 = 27배
```

각 계층 개발자는 "우리는 3번만 재시도한다"고 믿는다. 바닥에 있는 DB는 27배를 받는다. 계층이 하나 늘 때마다 배수는 곱해진다. 그래서 AWS Builders' Library의 권고는 단순하다 — **재시도는 스택에서 한 곳에만 둔다**. 보통 사용자와 가장 가까운 곳, 혹은 가장 바깥 한 곳이다.

두 번째 장치는 재시도 예산이다. AWS SDK의 standard 재시도 모드는 클라이언트마다 **500 토큰짜리 버킷**을 두고, 재시도 1회에 5 토큰(타임아웃성 오류는 10 토큰)을 차감한 뒤 성공하면 되돌려준다. 토큰이 마르면 재시도를 아예 포기한다. 구조는 [[rate-limit-token-bucket]]과 같은데, 제한하는 대상이 남의 트래픽이 아니라 **내가 만들어내는 재시도**다. Google SRE 책은 같은 아이디어를 비율로 쓴다 — 재시도가 전체 요청의 **10%를 넘지 않게** 클라이언트 쪽에서 묶는 방식이다.

### 재시도가 만드는 준안정 실패

가장 중요한 성질은 이거다. 재시도 루프는 **원인이 사라져도 스스로 지속된다**.

인과는 이렇게 닫힌다. 부하 급증 → 지연 증가 → 클라이언트 타임아웃 → 재시도 → 부하 더 증가 → 지연 더 증가. 트리거가 제거돼도 이 루프는 자기 입력을 자기가 공급하기 때문에 계속 돈다. 분산 시스템 연구에서 **metastable failure**라고 부르는 상태다. 시스템은 정상 상태와 "부하가 재시도로만 유지되는" 나쁜 안정 상태 두 개를 갖고, 한번 후자로 넘어가면 트리거를 없애는 것만으로는 못 돌아온다.

빠져나오는 길은 하나뿐이다. **입력을 강제로 끊는 것.** 재시도 끄기, 트래픽 드레인, [[circuit-breaker]] 강제 open — 다 같은 말이다. 루프에 공급되는 에너지를 잘라야 원래 상태로 떨어진다.

### 재시도해도 되는 실패인가

마지막 전제 조건. 타임아웃은 "실패했다"가 아니라 **"결과를 모른다"**는 뜻이다. 서버는 이미 주문을 만들었는데 응답만 못 받았을 수 있다. 이 상태에서의 재시도는 중복 생성이다. 그래서 재시도는 멱등성과 세트로만 성립한다 — [[idempotency-key]] 없이 켜는 재시도는 가용성 장치가 아니라 데이터 손상 장치다.

400/404/422 같은 클라이언트 오류는 몇 번을 보내도 같은 답이 온다. 재시도 대상은 429, 503, 그리고 커넥션 오류·타임아웃까지다. 429·503에 `Retry-After` 헤더가 붙어 오면 **내 백오프 계산보다 서버 값이 우선**이다.

## 현장 시나리오

주문 처리 API. 평시 8,000 RPS, 아키텍처는 API 게이트웨이 → 주문 서비스 → 재고 서비스 → PostgreSQL(Primary 1 + Replica 2). 세 계층 모두 라이브러리 기본값인 "3회 재시도, 100ms 고정 간격"으로 배포돼 있었다. 지터는 어디에도 없었다.

14:02, Primary 노드 하드웨어 이슈로 페일오버가 시작된다 → 승격까지 **2.1초** 동안 쓰기가 전부 실패한다 → 그 2.1초 안에 도착한 약 **17,000건**이 동시에 실패한다 → 100ms 뒤, 17,000건이 **한꺼번에** 재시도된다. 지터가 없으니 파형이 그대로 유지된다.

여기서 계층이 곱셈을 시작한다. 재고 서비스가 3번, 그걸 감싼 주문 서비스가 3번, 그 위 게이트웨이가 3번 → 새 Primary는 **평시 27배에 해당하는 요청**을 맞는다 → 커넥션 풀(서비스당 50개)이 즉시 마른다([[connection-pool-sizing]]) → 풀 대기 시간이 늘어 응답이 2초를 넘긴다 → 게이트웨이 타임아웃 2초에 걸려 **성공한 요청까지 실패로 집계되고 다시 재시도된다**.

14:02:03에 새 Primary는 이미 건강했다. 하지만 부하의 출처가 사용자에서 재시도로 바뀌어 있었다. 실제 주문 수는 그대로인데 DB가 받는 쿼리는 20배가 넘었다. 롤백할 배포도, 죽일 배치도 없었다. 대시보드에는 원인 없는 100%만 찍혔다.

40분 뒤, 게이트웨이에서 재시도를 0으로 내리고 트래픽을 30초 드레인한 다음 다시 열자 지표가 즉시 정상으로 떨어졌다. **장애는 2.1초였다. 나머지 40분은 우리가 만든 것이었다.**

## 실무 적용 포인트

1. **백오프를 쓴다면 지터는 옵션이 아니다.** `sleep = random(0, min(cap, base × 2^attempt))` — full jitter를 기본으로 잡는다. `base` 100ms, `cap` 20초, 최대 3~5회가 일반적인 출발점이다. 고정 간격 재시도는 동기화된 파형을 그대로 보존하므로 쓰지 않는다.

2. **재시도는 스택에서 한 계층에만 둔다.** 내부 호출 라이브러리의 기본 재시도를 명시적으로 끄고(대개 `maxAttempts=1`), 바깥 한 곳에만 남긴다. 계층 수 `L`, 계층당 시도 `n`이면 바닥이 받는 배수는 `n^L`이다. 3계층 × 3회면 27배다.

3. **클라이언트마다 재시도 예산을 건다.** AWS SDK standard 모드처럼 토큰 버킷(예: 500 토큰, 재시도당 5, 타임아웃 10, 성공 시 환급)을 쓰거나, SRE 책 방식으로 재시도를 전체 요청의 10% 이하로 묶는다. 예산이 마르면 즉시 실패시키는 게 맞다.

4. **재시도 가능 오류를 화이트리스트로 못 박는다.** 429·503·커넥션 오류·타임아웃만 재시도한다. 400·404·422는 절대 재시도하지 않는다. `Retry-After` 값이 오면 내 백오프 대신 그 값을 쓴다.

5. **멱등성 없는 엔드포인트에는 재시도를 켜지 않는다.** 쓰기 경로는 클라이언트 생성 idempotency key + 서버 저장(TTL 24시간 수준)이 선행 조건이다. `POST /orders`에 재시도를 켜기 전에 같은 키로 두 번 보냈을 때 주문이 하나만 생기는지부터 검증한다.

6. **"재시도 비율"을 지표로 뽑아 경보를 건다.** `retries / total_requests`가 평시 1~2%에서 10%를 넘으면 이미 증폭 루프에 진입한 것이다. 성공률·p99만 보면 이 전환을 놓친다. 대응 런북 1번 줄은 "재시도 끄고 드레인" — [[backpressure-patterns]]의 부하 차단과 같은 동작이다.
