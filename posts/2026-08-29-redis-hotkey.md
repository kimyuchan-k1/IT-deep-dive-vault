# 샤드를 6개에서 12개로 늘렸다. 그런데 더 느려졌다

Redis 클러스터 CPU가 한 노드만 100%였다. 나머지 다섯 노드는 8%였다. 노드를 6개에서 12개로 늘리고 슬롯을 재배치했다. 마이그레이션이 끝난 뒤 p99는 900ms에서 1,400ms가 됐다.

## 흔한 오해

> "핫키는 그 키를 담당하는 노드만 부하가 몰리는 문제니까, 샤드를 늘려서 부하를 쪼개면 된다."

[[redis-bigkey]]가 "큰 값 하나가 싱글 스레드를 막는 문제"였으니, 핫키는 "요청이 한쪽으로 쏠리는 문제"고 따라서 수평 확장으로 풀린다 — 이 추론은 자연스럽다. 대부분의 스케일아웃이 실제로 그렇게 작동하니까.

여기엔 두 가지가 빠져 있다. 하나는 **키 하나는 절대 쪼개지지 않는다**는 것. 다른 하나는 **핫키에서 먼저 포화되는 자원이 CPU가 아니라는 것**이다.

## 실제 원리

### 키 하나는 슬롯 하나, 슬롯 하나는 노드 하나

Redis Cluster는 키를 `CRC16(key) mod 16384`으로 슬롯에 매핑한다. 슬롯 16384개를 노드들이 나눠 갖는다. 리샤딩은 **슬롯 단위 이동**이다.

`product:flash:8842`는 항상 같은 슬롯 하나에 떨어진다. 노드를 6개로 늘리든 600개로 늘리든, 이 키의 요청은 전부 한 노드로 간다. 리샤딩이 바꾸는 건 "그 슬롯을 어느 노드가 갖는가"뿐이다. 핫키에 대해 수평 확장의 분모는 6도 12도 아니고 언제나 1이다.

### CPU보다 NIC가 먼저 죽는다

핫키 장애를 CPU 그래프로 진단하면 원인을 놓친다. 캐시 값이 18KB라고 하자.

```
18KB × 7,000 QPS = 126 MB/s ≈ 1.0 Gbps
```

1Gbps NIC는 **초당 7천 요청에서 포화**된다. GET은 O(1)이라 CPU는 아직 여유가 있다. 그런데 응답이 나갈 회선이 없다. 이때 나타나는 증상은 CPU 100%가 아니라 커널 송신 큐 적체와 재전송이고, 클라이언트 쪽에서는 그냥 "타임아웃"으로 보인다.

값이 200바이트면 이 한계는 60만 QPS로 올라간다. **핫키의 실제 임계값은 QPS가 아니라 `값 크기 × QPS`다.**

### 노드를 늘리면 왜 더 나빠지나

리샤딩은 핫 슬롯을 그대로 둔 채 세 가지 부담을 추가한다.

1. **마이그레이션 중 리디렉트**: 이동 중인 슬롯에 접근하면 `ASK`/`MOVED` 응답이 온다. 클라이언트는 한 번 더 왕복한다. 이미 회선이 포화된 노드에서 왕복이 두 배가 된다.
2. **클러스터 버스 트래픽**: 각 노드는 100ms마다 다른 노드들과 gossip을 주고받는다. 노드 수가 늘면 버스 메시지도 늘고, 이 트래픽은 데이터 트래픽과 **같은 NIC**를 쓴다.
3. **커넥션 수 증가**: 애플리케이션 100대가 노드당 커넥션 풀을 유지하면, 노드 12개에서는 유지해야 할 커넥션이 두 배가 된다. 핫 노드가 처리할 일이 줄지 않은 채 관리 부담만 는다.

핫키에서 리샤딩은 해결책이 아니라 부하 추가다.

## 현장 시나리오

커머스 타임세일. 오픈 10초 전부터 앱이 `product:flash:8842`를 폴링한다. 값은 상품 상세 JSON 18KB. 클러스터는 6노드, 각 노드 1Gbps.

오픈 순간 12만 QPS가 그 키 하나로 몰렸다. 슬롯 담당은 노드 3. 필요 대역폭은 18KB × 120,000 = 2.1GB/s, 회선 용량의 **17배**였다.

인과 사슬은 이렇게 흘렀다.

`NIC 포화` → 응답 지연 p99 3ms에서 900ms → 클라이언트 타임아웃 200ms 초과 → 자동 재시도로 실제 요청량 2.3배 증폭 → 타임아웃된 요청들이 캐시 미스로 처리되어 DB 조회 → DB 커넥션 풀 고갈 → 상품 페이지 전체 5xx.

당직자는 노드 3의 CPU가 62%인 것을 보고 "CPU는 여유 있으니 네트워크 문제는 아닐 것"이라 판단했고, 샤드를 12개로 늘렸다. 마이그레이션 중 `ASK` 리디렉트가 겹치면서 p99는 1,400ms가 됐다. 실제 수정은 애플리케이션에 300ms TTL 로컬 캐시를 넣는 배포 한 번이었다. 노드 3이 받는 실효 QPS는 100대 × (1초 / 0.3초) ≈ 333으로 떨어졌다.

## 실무 적용 포인트

1. **진단은 대역폭부터**. `INFO stats`의 `total_net_output_bytes` 증가율을 NIC 용량과 비교한다. CPU가 60%인데 지연이 튀면 회선을 먼저 의심한다. 키별 분포는 `redis-cli --hotkeys`로 보되, 이건 `maxmemory-policy`가 `allkeys-lfu`/`volatile-lfu`일 때만 동작한다.
2. **L1 로컬 캐시 100~500ms**. 핫키에 가장 효과가 큰 대응이다. TTL 300ms면 인스턴스 1대가 Redis로 보내는 요청은 초당 3회 이하로 고정된다. 트레이드오프는 최대 300ms의 stale 데이터다. 재고처럼 정확도가 필요한 값은 캐시하지 말고 카운터를 따로 둔다.
3. **키 복제 샤딩**. `product:flash:8842:0` 부터 `:9` 까지 10벌을 만들고 클라이언트가 랜덤으로 하나를 읽는다. 접미사가 CRC16 입력에 들어가야 하므로 **해시 태그 `{}`를 쓰면 안 된다**(`{}`로 감싸면 오히려 같은 슬롯에 모인다). 부하가 10개 슬롯으로 흩어진다. 대신 무효화 시 10개를 모두 지워야 한다.
4. **값 크기를 먼저 줄인다**. 18KB JSON에서 목록 렌더링에 필요한 6개 필드만 남기면 1.5KB가 된다. 같은 회선에서 처리 가능한 QPS가 12배가 된다. 대역폭 병목에서는 값 다이어트가 노드 추가보다 싸다.
5. **레플리카 읽기 분산**. `READONLY` 후 레플리카에서 읽으면 읽기 대역폭이 레플리카 수만큼 늘어난다. 복제는 비동기라 [[read-your-writes]]가 깨진다. 쓰기 직후 읽기가 필요한 경로는 프라이머리로 보낸다.
6. **재시도에 지터를 넣는다**. 타임아웃 재시도가 증폭의 절반을 만든다. [[retry-exponential-backoff-jitter]] 없이 즉시 재시도하면 포화된 노드를 계속 때린다.
7. **RESP3 클라이언트 사이드 캐싱**. Redis 6+의 `CLIENT TRACKING`은 서버가 무효화 메시지를 푸시한다. 로컬 캐시의 stale 창을 TTL이 아니라 무효화 시점으로 좁힐 수 있다.

## 더 깊은 토끼굴

핫키와 [[cache-stampede]]는 같은 사건의 앞뒤다. 핫키가 타임아웃을 만들고, 타임아웃이 미스가 되어 스탬피드로 번진다. 슬롯 매핑이 왜 16384개인지는 [[redis-cluster-slot]]에서, 만료 타이밍이 부하를 어떻게 동기화시키는지는 [[redis-ttl-eviction]]에서 이어진다. [[redis-bigkey]]가 CPU 시간을 잡아먹는 문제라면 핫키는 회선을 잡아먹는 문제다.
