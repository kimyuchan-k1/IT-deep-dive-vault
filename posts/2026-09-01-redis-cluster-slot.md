# 노드를 6대에서 12대로 늘렸다. 그런데 한 대만 CPU 100%였다

## 흔한 오해

> "슬롯이 16384개나 되는데 키가 한쪽으로 몰릴 리가 있나? 노드를 늘리면 슬롯이 나눠지고 부하도 같이 나눠지는 거 아닌가?"

Redis Cluster를 처음 붙일 때 거의 모두가 이렇게 이해한다. 통념의 출처도 명확하다. 공식 소개 문서의 첫 문장이 "키 공간을 16384개 해시 슬롯으로 나눈다"이기 때문이다. 슬롯 수가 노드 수보다 세 자릿수 크니까, 자연스럽게 "충분히 잘게 쪼개져 있다"로 읽힌다.

틀린 건 아닌데, 두 가지를 빼먹었다. **해시 함수에 들어가는 입력이 키 전체가 아닐 수 있다**는 것, 그리고 **슬롯은 쪼갤 수 없는 원자 단위**라는 것.

## 실제 원리

### 16384는 성능 최적화 숫자가 아니다

키가 어느 슬롯에 가는지는 한 줄로 끝난다.

```
HASH_SLOT = CRC16(key) mod 16384
```

여기서 나오는 첫 질문이 "왜 하필 16384인가"다. 2의 거듭제곱을 쓸 거면 65536도 되고 4096도 된다. antirez가 직접 답한 이유는 성능이 아니라 **가십 프로토콜 패킷 크기**였다.

Redis Cluster의 노드들은 클러스터 버스로 계속 하트비트를 주고받는다. 이 패킷에는 보내는 노드가 담당하는 슬롯 정보가 **비트맵 통째로** 실린다. 슬롯 1개당 1비트다.

- 16384 슬롯 → 16384비트 = **2048바이트 (2KB)**
- 65536 슬롯 → 65536비트 = **8192바이트 (8KB)**

노드는 상대를 `cluster-node-timeout`의 절반 안에 최소 한 번은 핑한다. 노드 수가 늘면 이 트래픽은 대략 제곱으로 붙는다. 헤더 하나가 8KB냐 2KB냐는 그 지점에서 4배 차이가 된다.

두 번째 이유는 반대편 제약이다. Redis Cluster는 마스터 1000대를 넘길 설계가 아니다. 마스터 1000대 기준으로 16384/1000 ≈ 16슬롯이면 재분배 입도로는 충분하다. 슬롯을 더 잘게 쪼개서 얻을 게 없다.

세 번째는 압축이다. 비트맵은 압축해서 보내는데, 노드 수 N이 작으면 각 노드가 16384/N 비트를 세팅한다. 세팅된 비트 비율이 높을수록 압축이 안 먹는다. 슬롯 수를 키우면 그 비압축 크기가 그대로 커진다.

정리하면 16384는 **가십 패킷 크기와 리샤딩 입도 사이의 타협값**이다. "빠른 나머지 연산" 같은 이유가 아니다.

### 해시 함수는 키 전체를 안 볼 수도 있다

멀티키 명령(`MGET`, `MSET`, `SUNION`, 트랜잭션, Lua)은 모든 키가 같은 슬롯에 있어야 동작한다. 아니면 이 에러가 난다.

```
CROSSSLOT Keys in request don't hash to the same slot
```

그래서 Redis는 탈출구를 하나 뒀다. 키에 `{`가 있고 그 뒤에 `}`가 있으며 그 사이가 비어 있지 않으면, **CRC16에 들어가는 건 그 중괄호 안 문자열뿐**이다. 나머지는 무시된다.

`user:{1000}:profile`과 `order:{1000}:items`는 둘 다 `1000`만 해싱되므로 같은 슬롯에 앉는다. 의도한 대로 쓰면 강력하다. 여기서 핵심은 규칙이 **첫 번째 `{`와 그 뒤 첫 번째 `}`**만 본다는 것이다. 키 안에 중괄호가 여러 쌍 있어도 뒤쪽은 아무 역할을 안 한다. 이 한 줄을 놓치면 설계 전체가 뒤집힌다.

### 슬롯은 마이그레이션의 최소 단위다

리샤딩은 슬롯 단위로만 움직인다. `CLUSTER SETSLOT <slot> MIGRATING`을 소스에, `IMPORTING`을 타깃에 걸고, `CLUSTER GETKEYSINSLOT`으로 키를 뽑아 `MIGRATE`로 밀어넣는 식이다.

이동 중에 그 슬롯으로 요청이 오면 소스 노드가 판단한다. 키가 아직 있으면 그냥 처리하고, 없으면 `ASK` 리다이렉트를 준다. 클라이언트는 타깃에 `ASKING`을 먼저 보내고 재요청한다. `MOVED`는 영구 이전이라 클라이언트가 슬롯맵을 갱신하지만, `ASK`는 **그 요청 1회짜리**다. 슬롯맵을 갱신하면 안 된다.

여기가 결정적이다. **한 슬롯을 두 노드에 나눠 담는 방법은 없다.** 슬롯 하나가 뜨거우면 노드를 아무리 추가해도 그 슬롯은 통째로 어느 한 노드에 착지한다. 게다가 `MIGRATE`는 소스와 타깃 양쪽에서 동기로 블로킹된다. 슬롯 안에 큰 키가 섞여 있으면 옮기는 동안 두 노드가 같이 멈춘다 — [[redis-bigkey]]가 리샤딩 중에 특히 위험한 이유다.

## 현장 시나리오

커머스, Redis Cluster 마스터 6 + 레플리카 6. 타임세일 재고 차감을 Lua로 원자 처리하기로 했다. Lua는 여러 키를 만지므로 같은 슬롯이어야 한다. 첫 배포에서 `CROSSSLOT` 에러를 만났고, 검색해서 해시태그를 찾았고, 키 템플릿을 이렇게 고쳤다.

```
promo:{2026-summer}:stock:{sku}
```

의도는 "세일 단위로 묶고 SKU로 나눈다"였다. 실제 동작은 다르다. 태그로 잡히는 건 첫 번째 중괄호 쌍뿐이라, 모든 상품 키의 해시 입력이 `2026-summer` 하나로 같아졌다. 3만 개 SKU가 슬롯 1개에 앉았다.

인과 사슬:

```
태그 {2026-summer} 고정 → SKU 3만 개가 전부 슬롯 1개
  → 세일 트래픽 전량이 마스터 1대로
  → 그 노드 CPU 100%, p99 2ms → 380ms
  → 대응: 마스터 6대 → 12대 증설 + 슬롯 재분배
  → 슬롯은 원자 단위, 문제 슬롯은 통째로 새 노드 1대에 착지
  → 지연 그대로. 인프라 비용만 2배
```

증설이 헛돌았다는 걸 확인한 건 `CLUSTER COUNTKEYSINSLOT`이었다. 한 슬롯에만 키가 3만 개, 나머지 16383개 슬롯은 합쳐서 4만 개였다. `redis-cli --cluster info`의 노드별 키 개수만 봤어도 편차가 먼저 보였을 지표였다.

고친 방법은 노드 증설이 아니라 키 설계였다. 태그를 `{sku}`로 내리고, Lua가 여러 SKU를 한 번에 만지던 부분은 SKU별 스크립트로 쪼갰다. **원자성이 필요한 경계가 세일 전체가 아니라 상품 하나였다는 게 처음부터의 진실이었다.**

## 실무 적용 포인트

1. **해시태그는 "반드시 원자적으로 같이 만져야 하는 최소 묶음"에만 붙인다.** 태그 후보는 사용자 ID·주문 ID처럼 카디널리티가 높은 값이다. 세일명·날짜·카테고리 같은 저카디널리티 상수는 금지다. 배포 전에 샘플 키 100개를 `CLUSTER KEYSLOT`으로 찍어 서로 다른 슬롯에 흩어지는지 눈으로 확인한다.
2. **슬롯 편중은 `CLUSTER COUNTKEYSINSLOT`으로 확인하되, 16384번 돌기 전에 `redis-cli --cluster info`부터 본다.** 노드별 키 수 편차가 20%를 넘으면 태그를 의심한다.
3. **`CROSSSLOT` 에러를 해시태그로 덮지 마라.** 그 에러는 "키 설계가 트랜잭션 경계와 안 맞는다"는 신호다. 대부분은 태그를 붙일 게 아니라 애플리케이션에서 키별로 나눠 파이프라이닝하는 게 맞다 — [[redis-pipelining-vs-tx]].
4. **리샤딩 전에 `redis-cli --bigkeys`를 먼저 돌린다.** `MIGRATE`는 동기 블로킹이고 `redis-cli --cluster`의 `--cluster-pipeline` 기본값은 10(한 번에 옮기는 키 수)이다. 큰 키가 배치에 섞이면 그 배치가 통째로 멈춘다.
5. **`cluster-require-full-coverage` 기본값은 `yes`다.** 슬롯 하나라도 담당 노드가 없으면 클러스터 전체가 `CLUSTERDOWN`으로 응답을 거부한다. 순수 캐시 용도라면 `no`로 두고 부분 가용성을 택하는 편이 낫다. 대신 그 구간 미스가 원본 DB로 그대로 간다 — [[cache-stampede]]를 같이 봐야 한다.
6. **`cluster-node-timeout` 기본값 15000ms를 함부로 낮추지 마라.** 낮추면 페일오버는 빨라지지만 노드들이 timeout의 절반 안에 서로 핑하므로 가십 트래픽이 올라간다. 앞에서 계산한 2KB 비트맵이 여기서 곱해진다.

## 더 깊은 토끼굴

핫슬롯은 [[redis-hotkey]]와 증상이 비슷하지만 대응이 완전히 다르다. 핫키는 키가 1개라 로컬 캐시나 복제본 읽기로 완화할 여지가 있다. 핫슬롯은 키가 수만 개인데 좌표가 같은 것이라, 키 이름을 고치는 것 말고는 방법이 없다.

슬롯이라는 고정 개수 중간층을 두는 설계가 왜 나왔는지는 [[sharding-strategies]]와 [[consistent-hashing]]으로 이어진다. 노드 수로 직접 모듈로를 하면 노드 1대 추가에 거의 모든 키가 이사해야 한다. 슬롯을 끼워두면 이사하는 건 슬롯 소유권뿐이다. 리샤딩 중 `MIGRATE`가 블로킹이라는 사실은 [[lazy-freeing]]이 클러스터 운영에서 왜 중요한지로 연결된다.
