# 읽기는 락을 안 걸어서 공짜인 줄 알았다. 리포트 배치 하나가 테이블을 4배로 불렸다

## 흔한 오해

> "MVCC를 쓰면 읽기가 쓰기를 막지 않고 쓰기가 읽기를 막지 않는다. 그러니까 SELECT는 락을 안 걸고, 락 경합을 걱정할 일이 없다."

문서에 실제로 그렇게 적혀 있으니 틀린 말은 아니다. PostgreSQL 매뉴얼도, MySQL 매뉴얼도 같은 문장을 쓴다. 그래서 대부분 여기서 읽기를 멈춘다.

멈춘 자리 바로 다음에 중요한 게 있다. **MVCC는 락이라는 비용을 없앤 게 아니라, 다른 축으로 옮긴 것이다.** 옮겨간 곳은 시간과 저장 공간이다. 락 대기 시간은 사라졌는데, 대신 "언제 이 옛 버전을 버려도 되는가"라는 문제가 생겼다. 그리고 그 문제는 대기 큐가 아니라 디스크 사용량과 스캔 비용으로 나타나기 때문에, 락 모니터링에는 절대 안 잡힌다.

## 실제 원리

### 버전은 어디에 쌓이는가

핵심은 "옛 버전을 어디에 두느냐"다. 두 엔진이 정반대 선택을 했다.

**PostgreSQL은 테이블 안에 쌓는다.** 힙 튜플마다 `xmin`(이 버전을 만든 트랜잭션 ID)과 `xmax`(이 버전을 지운 트랜잭션 ID)가 붙어 있다. `UPDATE`는 제자리 수정이 아니다. 새 튜플을 뒤에 붙이고, 옛 튜플의 `xmax`에 자기 XID를 찍는 것으로 끝난다. 즉 Postgres에서 `UPDATE` 한 번은 물리적으로 `INSERT` + 논리적 `DELETE`다. 옛 버전은 같은 테이블 파일 안에 시체(dead tuple)로 남는다.

**InnoDB는 테이블 밖에 쌓는다.** 클러스터 인덱스 레코드를 제자리에서 고치고, 직전 이미지는 undo 로그에 넣는다. 레코드에 `DB_TRX_ID`와 `DB_ROLL_PTR`이 있어서, 옛 스냅샷을 보는 트랜잭션은 `DB_ROLL_PTR`을 따라 undo 체인을 거꾸로 되감아 자기 시점의 행을 **재구성**한다.

이 차이가 비용의 위치를 결정한다. Postgres는 읽기가 싸다(그냥 헤더 비교). 대신 테이블이 부풀고 청소가 필요하다. InnoDB는 테이블이 안 부푼다. 대신 체인이 길어지면 읽기 자체가 느려진다. 같은 SELECT가 undo를 수천 번 되감을 수 있다.

### 스냅샷은 시계가 아니라 명단이다

"트랜잭션 시작 시점의 사진"이라는 비유가 오해를 부른다. 스냅샷은 타임스탬프가 아니라 **그 순간 실행 중이던 트랜잭션 ID 목록**이다. Postgres 기준으로 `xmin`(활성 트랜잭션 중 최소 XID), `xmax`(아직 배정 안 된 다음 XID), 그리고 그 사이에서 아직 안 끝난 XID들의 목록을 들고 다닌다. 튜플 하나를 볼 때마다 "이 `xmin`이 커밋됐고 내 스냅샷보다 앞서는가"를 판정한다.

여기서 결정적인 사실 하나. 시스템 전체에서 **가장 오래된 스냅샷 하나**가 청소의 하한선을 잡는다. 어떤 트랜잭션이 4시간 전 스냅샷을 들고 있으면, 그 4시간 동안 만들어진 모든 dead tuple은 아직 누군가에게 보일 수 있으므로 회수 불가다. 트랜잭션 하나가 아무 락도 안 잡고, 아무 쿼리도 안 돌리면서, 테이블 전체의 청소를 막을 수 있다는 뜻이다.

### 청소를 못 하면 어디가 아픈가

Dead tuple은 그냥 자리만 차지하는 게 아니다. 인덱스에는 **살아있는 튜플과 죽은 튜플 양쪽을 가리키는 엔트리가 다 들어 있다.** 인덱스 스캔이 조건에 맞는 엔트리를 100개 찾으면, 그중 90개가 시체라도 일단 힙 페이지를 방문해서 가시성을 확인해야 한다. 이건 [[btree-index-internals]]에서 말한 팬아웃 이득을 그대로 반납하는 동작이다.

Index Only Scan은 더 직접적으로 무너진다. 이 계획은 visibility map에서 "이 페이지는 전부 살아있음" 표시를 보고 힙 방문을 건너뛰는 건데, VACUUM이 그 표시를 세워주는 주체다. 청소가 멈추면 표시가 안 서고, Index Only Scan이 조용히 Index Scan으로 퇴화한다. 실행 계획 이름은 그대로인데 `Heap Fetches` 숫자만 폭발한다.

## 현장 시나리오

주문 데이터 3천만 행, `orders` 테이블. 매일 새벽 2시에 BI팀 배치가 월간 정산 리포트를 뽑는다. 배치는 트랜잭션을 열고 여러 쿼리를 순차 실행한 뒤 마지막에 커밋하는 구조였다. 중간에 외부 정산 API를 호출하는 단계가 있었는데, 상대 쪽이 느려지면서 이 단계가 **3~4시간씩 대기**하기 시작했다. 트랜잭션은 그동안 `idle in transaction` 상태로 열려 있었다.

낮 시간대 주문 상태 업데이트는 평소대로 초당 수백 건 들어왔다. 그 UPDATE들이 만든 dead tuple을 autovacuum이 매번 시도했지만, 배치가 잡고 있는 `backend_xmin`보다 최신인 튜플은 하나도 회수하지 못했다. 로그에는 성공으로 찍혔다. 회수된 튜플 수만 0에 가까웠다.

일주일 뒤 `orders` 테이블 크기가 42GB에서 168GB로 늘었다. 살아있는 행은 그대로였다. [[innodb-buffer-pool]]에 해당하는 Postgres의 shared buffers 적중률이 무너졌고, 주문 조회 API p99가 40ms에서 1.2초가 됐다. 팀은 처음에 인덱스를 의심해서 새 인덱스를 만들었다. 인덱스도 부푼 테이블을 가리키니 아무 효과가 없었다.

원인은 락 하나 안 잡은 SELECT 트랜잭션이었다. `pg_stat_activity`에서 `state = 'idle in transaction'`이고 `xact_start`가 4시간 전인 행 하나. 그 배치의 트랜잭션 경계를 API 호출 앞뒤로 쪼개는 것만으로 다음 날 autovacuum이 정상 회수를 재개했다.

## 실무 적용 포인트

1. **가장 오래된 트랜잭션을 상시 감시한다.** Postgres에서 `SELECT max(now() - xact_start) FROM pg_stat_activity WHERE state <> 'idle'`를 알람에 건다. 임계값 5분이면 대부분의 OLTP 서비스에 충분하다. 락 대기가 아니라 **트랜잭션 나이**를 봐야 한다.
2. **`idle_in_transaction_session_timeout`을 반드시 설정한다.** 기본값은 0(무제한)이다. 애플리케이션 DB 롤에 `30s`~`60s`를 걸면 이번 사고 유형은 구조적으로 막힌다. 배치 롤에만 예외를 주는 게 낫다.
3. **트랜잭션 안에서 외부 I/O를 하지 않는다.** HTTP 호출, S3 업로드, 메시지 발행은 트랜잭션 밖으로 뺀다. 굳이 원자성이 필요하면 [[outbox-pattern]]을 쓴다. 이 규칙 하나가 MVCC 사고의 절반을 없앤다.
4. **큰 테이블은 autovacuum 임계를 낮춘다.** `autovacuum_vacuum_scale_factor` 기본값 0.2는 "죽은 행이 전체의 20%가 되면 청소"라는 뜻이다. 3천만 행이면 600만 개가 쌓일 때까지 기다린다. 대형 테이블에 한해 테이블 단위로 `0.02`, `autovacuum_vacuum_threshold`를 `5000` 정도로 낮춘다.
5. **`fillfactor`로 HOT 업데이트를 유도한다.** 인덱스 걸린 컬럼을 안 바꾸는 UPDATE는 같은 페이지에 여유가 있으면 인덱스 갱신 없이 처리된다(HOT). 갱신이 잦은 테이블은 `ALTER TABLE ... SET (fillfactor = 85)`로 페이지에 여유를 만든다. 새로 쓰이는 페이지부터 적용된다.
6. **InnoDB는 다른 지표를 본다.** bloat 대신 `SHOW ENGINE INNODB STATUS`의 History list length를 감시한다. 수십만 이상으로 올라가면 purge가 밀린 것이고, 증상은 테이블 크기가 아니라 **읽기 지연**으로 나타난다. `information_schema.innodb_trx`로 장수 트랜잭션을 같은 방식으로 잡는다.
7. **MVCC가 격리 수준을 다 해결해주지 않는다.** 스냅샷 격리에서도 write skew는 남는다. 두 트랜잭션이 각자 스냅샷을 읽고 서로의 전제를 깨는 쓰기를 하는 경우다. 정합성이 필요한 지점은 `SELECT ... FOR UPDATE`(MVCC 밖의 실제 락)나 `SERIALIZABLE`을 명시적으로 쓴다. 자세한 건 [[phantom-read-isolation]].

읽기가 락을 안 잡는다는 문장은 사실이다. 그런데 그 문장은 "읽기가 시스템에 아무 영향도 안 준다"는 뜻이 아니다. MVCC에서 읽기 트랜잭션은 락 대신 **시간을 붙잡는다.** 붙잡은 시간만큼 데이터베이스는 과거를 버리지 못한다.
