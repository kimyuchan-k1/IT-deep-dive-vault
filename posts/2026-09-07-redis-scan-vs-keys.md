# KEYS를 SCAN으로 바꿨다. Redis는 더 오래 멈췄다

## 흔한 오해

> "`KEYS *`는 O(N)이라 위험하고, `SCAN`은 커서로 나눠 도니까 안전하다."

그래서 코드 리뷰에서 `KEYS`가 보이면 `SCAN`으로 바꾸라는 코멘트가 달리고, 바꾸면 그걸로 끝난 걸로 친다. Redis 공식 문서 자체가 `KEYS`를 "프로덕션에서 쓰지 마라"고 명시하니 자연스러운 반응이다.

절반만 맞다. **`SCAN`이 안전한 이유는 "나눠서" 돌기 때문이 아니라, "한 번의 호출이 짧기" 때문이다.** 그 전제를 깨는 파라미터가 `SCAN` 자신에 붙어 있다. `COUNT`다.

## 실제 원리

### 1. SCAN은 키가 아니라 버킷을 센다

Redis의 키 스페이스는 체이닝 방식 해시 테이블(`dict`)이다. `SCAN`이 반환하는 커서는 "몇 번째 키까지 봤다"가 아니라 **버킷 인덱스**다. `COUNT`도 "키 N개 달라"가 아니라 **"버킷 N개를 훑어라"는 힌트**다.

그래서 `COUNT 100000`은 한 번의 호출에서 버킷 10만 개를 순회하고, 그 안에 매달린 키를 전부 꺼내 `MATCH` 패턴 매칭까지 돌린다. Redis는 싱글 스레드다. 그동안 다른 명령은 한 줄도 처리되지 않는다. `KEYS`를 손으로 잘라 붙인 것과 같아진다.

`COUNT` 기본값은 10이다. 이 값이 작은 건 성능 미달이 아니라 **설계 의도**다.

### 2. 커서는 왜 1씩 안 늘어나는가 — 역방향 이진 증가

`SCAN`의 진짜 어려운 문제는 순회 중에 테이블이 리해시되는 것이다. 키가 늘면 dict는 두 배로 커지고, 줄면 절반으로 줄어든다. 버킷을 0, 1, 2, 3… 순서로 돌다가 테이블이 두 배가 되면 이미 지나온 버킷의 키가 아직 안 본 위치로 튈 수도, 아직 안 본 키가 지나온 위치로 밀릴 수도 있다.

Redis는 커서를 **비트를 뒤집어서 증가**시킨다. 커서 비트를 리버스 → 1 더하기 → 다시 리버스. 버킷 4개(마스크 `0b11`)짜리 테이블이면 순회 순서가 이렇게 된다.

```
일반 증가:      00 → 01 → 10 → 11
역방향 이진:    00 → 10 → 01 → 11
                 (상위 비트부터 캐리가 전파)
```

이 순서의 성질이 핵심이다. 테이블이 4개 → 8개로 커지면 옛 버킷 `1`의 키는 새 버킷 `1`과 `5`로 갈라진다. 역방향 이진 순서에서는 **이미 방문한 버킷이 분열해서 생긴 새 버킷들이 항상 아직 방문하지 않은 구간에 몰리거나, 이미 다 커버된 상태가 된다.** 테이블이 커지든 작아지든 누락이 없다.

리해시가 진행 중이면 `ht[0]`과 `ht[1]`이 동시에 존재한다. 이때 `SCAN`은 작은 테이블의 버킷 하나를 본 뒤, 큰 테이블에서 그 버킷으로 매핑되는 버킷들을 전부 이어서 훑는다.

### 3. 그래서 보장이 이렇게 약하다

역방향 이진 순회가 사주는 보장은 딱 하나다. **순회 시작 시점부터 끝 시점까지 계속 존재한 원소는 최소 한 번 반환된다.** 그 이상은 없다.

- 같은 키가 **여러 번** 반환될 수 있다
- 순회 중에 추가/삭제된 키는 반환될 수도, 안 될 수도 있다
- **빈 배열이 반환될 수 있다.** `MATCH`는 버킷을 훑은 *다음에* 거는 필터라서, 10개 버킷에 패턴 일치가 없으면 그냥 빈 배열이 온다

마지막 항목이 사고를 만든다.

## 현장 시나리오

이커머스 세션 스토어. 키 2,000만 개. 만료 정책이 꼬여 남은 `session:expired:*` 키를 지우는 배치를 야간에 돌리기로 했다. 처음 코드는 `KEYS session:expired:*`였고, 리뷰에서 반려돼 `SCAN`으로 바뀌었다.

배치 로직이 이랬다.

```python
keys = r.scan(0, match="session:expired:*", count=1000)[1]
while keys:                      # ← 종료 조건이 배열
    delete(keys)
    keys = r.scan(0, match=..., count=1000)[1]   # ← 커서도 항상 0
```

첫 배치 실행: 2,000만 개 중 패턴 일치는 앞쪽 버킷에 거의 없다. 커서 0에서 시작한 첫 호출이 **빈 배열**을 반환한다. 루프는 "다 지웠다"고 판단하고 즉시 끝난다. 지워진 키는 0개. 배치는 "성공"으로 로깅됐다.

한 주 뒤 메모리 경보가 뜬다. 개발자는 "`SCAN`이 너무 조금씩 가져와서 그렇다"고 진단하고 `COUNT`를 `100000`으로 올린다. 이제 첫 호출이 버킷 10만 개를 훑고 그 안의 키 수십만 개에 `session:expired:*` 글롭 매칭을 돌린다. 한 호출이 **120ms 블로킹**. 커서는 여전히 0으로 고정이라 같은 구간을 반복한다.

인과 사슬은 이렇게 갔다. 커서 재사용 버그 → 같은 앞쪽 버킷 반복 순회 → `COUNT` 인상으로 호출당 120ms 블로킹 → 배치 루프가 초당 8회 → 사실상 상시 점유 → 로그인 API p99 6ms에서 340ms → 커넥션 풀 대기 → 앱 타임아웃 → 클라이언트 재시도로 부하 증폭. 호출 하나하나는 `cluster-node-timeout`을 넘지 않아 페일오버는 안 났다. 그래서 알람이 안 울렸고, 40분간 아무도 Redis를 의심하지 않았다.

`SLOWLOG GET`을 찍고 나서야 `SCAN 0 MATCH session:expired:* COUNT 100000`이 수백 줄 쌓여 있는 게 보였다. 커서가 전부 `0`이었다.

## 실무 적용 포인트

1. **종료 조건은 반환 배열이 아니라 커서다.** `while cursor != 0`으로 돌고, 매 호출마다 반환된 커서를 다음 호출에 넣는다. 빈 배열은 정상 응답이지 종료 신호가 아니다.
2. **`COUNT`는 100~1000을 넘기지 마라.** 기본 10, 대량 순회 배치도 1000이면 충분하다. 10000 이상은 `KEYS`로 회귀하는 구간이다. `slowlog-log-slower-than 10000`(10ms)을 걸고 `SLOWLOG GET`에 `SCAN`이 올라오는지 본다.
3. **`MATCH`는 인덱스가 아니라 사후 필터다.** 패턴이 아무리 좁아도 키 2,000만 개면 버킷 2,000만 개어치 순회 비용을 그대로 낸다. 특정 집합을 자주 훑어야 하면 Set이나 Sorted Set으로 별도 인덱스 키를 유지하는 게 맞다.
4. **클러스터에서 `SCAN`은 노드 단위다.** 커서는 노드마다 독립이라, 클라이언트가 마스터 노드를 순회하며 각각 커서를 0부터 끝까지 돌려야 전체 키가 나온다. 노드 하나만 돌고 "전체 스캔했다"고 믿으면 슬롯 범위만큼 빠진다 → [[redis-cluster-slot]]
5. **중복 반환을 전제로 처리를 멱등하게 짜라.** 같은 키가 두 번 오면 삭제는 문제없지만 카운터 증가는 틀어진다. 삭제는 `DEL` 대신 `UNLINK`로 백그라운드 회수를 태운다 → [[lazy-freeing]]
6. **`HSCAN`/`SSCAN`/`ZSCAN`은 listpack 인코딩이면 `COUNT`를 무시하고 전부 한 번에 반환한다.** `hash-max-listpack-entries`(기본 128) 아래에서는 커서가 항상 0으로 끝난다. 작은 컬렉션에서는 애초에 나눠 돌지 않는다는 뜻이고, 그 컬렉션이 임계를 넘어 hashtable로 승격되는 순간 동작이 바뀐다 → [[redis-bigkey]]
7. Redis 6.0부터 `SCAN cursor TYPE string`으로 타입 필터가 가능하다. 이것도 사후 필터라 순회 비용은 안 줄여준다.

요약: `SCAN`은 "안전한 `KEYS`"가 아니다. **한 호출을 짧게 유지하는 계약**이고, `COUNT`를 올리는 순간 그 계약을 개발자가 직접 파기하는 것이다. [[redis-hotkey]]와 마찬가지로, 문제는 명령어가 아니라 명령어에 붙인 숫자에 있다.
