# 왕복 한 번을 아꼈다. 결제가 두 번 찍혔다

## 흔한 오해

> "TLS 1.3은 handshake가 1-RTT라 빠르다. 거기다 0-RTT를 켜면 왕복이 아예 0이 된다. 재접속하는 클라이언트는 첫 패킷에 요청까지 실어 보내니 공짜로 100ms를 번다. 켜면 이득이다."

앞부분은 정확하다. TLS 1.2는 handshake에 2 왕복이 필요했고, TLS 1.3은 첫 메시지에 `key_share`를 미리 실어 1 왕복으로 줄였다. 0-RTT는 그 1 왕복마저 없앤다.

문제는 "공짜"다. 0-RTT가 없앤 왕복의 정체는 **서버가 이 요청을 처음 보는지 확인하는 왕복**이다. RFC 8446이 이 기능만 따로 절을 떼어 보안 속성이 다르다고 경고하는 이유다.

## 실제 원리

### 1. 1-RTT handshake가 왜 1-RTT인가

TLS 1.3 클라이언트는 `ClientHello`에서 서버가 고를 곡선을 **추측해서** 그 곡선의 공개키(`key_share`)를 같이 보낸다. 대개 X25519다. 서버가 `ServerHello`에 자기 `key_share`를 실어 답하는 순간 양쪽이 ECDHE 공유 비밀을 갖는다.

```
Client                                  Server
ClientHello + key_share      -------->
                                        ServerHello + key_share
                                        {EncryptedExtensions}
                                        {Certificate}
                                        {CertificateVerify}
                             <--------  {Finished}
{Finished}
[Application Data]           -------->        ← 1 왕복 후 첫 요청
```

추측이 틀리면 `HelloRetryRequest`로 곡선을 다시 지정하고 이때만 2 왕복이 된다. TLS 1.2는 암호 스위트를 합의한 **다음에야** 키 교환을 시작해서 구조적으로 2 왕복이었다.

### 2. 0-RTT는 과거의 비밀을 재사용한다

한 번 붙었던 서버는 `NewSessionTicket`을 내려준다. 티켓 안에는 resumption master secret에서 파생된 PSK가 있다. 다음 접속 때 클라이언트는 이렇게 한다.

```
ClientHello
  + pre_shared_key        ← 예전 티켓
  + early_data            ← "요청 실어 보낸다"
  + key_share             ← 이후 통신용 새 ECDHE
[Early Application Data]  ← 여기. 왕복 0번.
```

핵심은 early data를 암호화하는 키가 어디서 나오는지다. 키 스케줄상 `client_early_traffic_secret`은 Early Secret에서 나오고, Early Secret의 입력은 **PSK 하나뿐이다**. 이번 연결의 새 ECDHE 값은 아직 섞이지 않았다. 결과가 둘이다.

**첫째, early data에는 전방 비밀성이 없다.** 서버의 세션 티켓 암호화 키(STEK)가 나중에 유출되면 녹음해둔 early data는 전부 복호화된다. handshake 이후 데이터는 ECDHE가 섞여 안전하지만 early data만 예외다.

**둘째, 리플레이를 막을 구조가 없다.** 1-RTT handshake에서는 서버가 새 난수를 섞기 때문에 옛 `ClientHello`를 재생해도 키가 달라져 이후 데이터가 안 풀린다. early data는 서버가 아무것도 기여하기 전에 이미 완성된 암호문이다. 통째로 복사해 다시 보내면 **서버 입장에서 완전히 정상인 요청**이다.

### 3. 그래서 방어는 "기억"밖에 없다

RFC 8446 8절의 대응은 전부 서버가 뭔가를 기억하는 방식이다.

1. **단일 사용 티켓** (8.1) — 티켓 하나를 한 번만 받아주고 쓴 ID를 지운다.
2. **ClientHello 기록** (8.2) — strike register. ClientHello 해시를 일정 시간 보관하고 중복이면 early data를 거절한다.
3. **freshness 검사** (8.3) — 티켓의 `ticket_age`와 서버가 잰 경과 시간을 비교해 창을 좁힌다.

셋 다 **상태를 공유해야** 성립한다. 여기가 실무에서 무너진다. 엣지 PoP 40곳, 각 PoP 안에 TLS 종단 서버 수십 대. strike register를 전 세계에 강한 일관성으로 복제하는 순간 아끼려던 1 왕복보다 비싸진다. 그래서 현실의 구현은 거의 전부 기록을 **서버 로컬** 또는 **PoP 로컬**에 둔다.

공격자는 이 틈을 그대로 쓴다. 캡처한 early data 한 덩이를 서울·도쿄·프랑크푸르트에 각각 던진다. 각 PoP는 그 ClientHello를 처음 본다. 전부 통과한다.

그래서 RFC 8446 부록 E.5는 이렇게 못 박는다. 프로토콜이 리플레이를 막아주리라 기대하지 말고 **리플레이당해도 안전한 요청만 early data로 허용**하라. RFC 8470은 그 위에 HTTP 규칙을 얹었다. 오리진이 early data 요청을 처리하기 싫으면 `425 Too Early`를 내리고, 클라이언트는 handshake 완료 후 다시 보낸다.

## 현장 시나리오

포인트 적립 API를 운영하던 커머스 팀이 CDN 엣지에서 0-RTT를 켰다. 3G/LTE 혼재 사용자 RTT가 120ms대라 TTFB p75가 110ms 줄었다.

문제는 앱이 `POST /v1/points/redeem`을 재접속 직후 첫 요청으로 보냈다는 점이다. 화면 진입, 커넥션 재개, 적립 요청. 앱 입장에선 자연스러운 순서였다.

공개 와이파이의 공격자가 자기 기기 요청을 캡처했다. TLS라 내용은 못 읽는다. 읽을 필요도 없었다. `ClientHello` + early data 레코드를 바이트째 복사해 서로 다른 엣지 IP 세 곳에 던졌다.

```
캡처된 early data 1개
  → 엣지 A: strike register에 없음 → 통과 → 오리진 적립 +5000
  → 엣지 B: 다른 PoP, 기록 없음   → 통과 → 오리진 적립 +5000
  → 엣지 C: 다른 PoP, 기록 없음   → 통과 → 오리진 적립 +5000
```

오리진 로그에는 정상 요청 세 건이 남았다. 인증 토큰도, TLS 세션도, 페이로드도 전부 유효하다. 스크립트로 하루 2,400회를 돌려 누적 1,200만 포인트가 발행됐고, 발견은 3일 뒤 회계 정산에서 발행량이 주문 건수와 안 맞는다는 보고로 올라왔다.

원인 한 줄. 리플레이 방어 주체가 TLS라고 믿었는데, TLS는 그 책임을 애플리케이션에 넘긴다고 명시해뒀다.

## 실무 적용 포인트

1. **early data는 GET/HEAD만 허용한다.** nginx에서 `ssl_early_data on;`을 켤 땐 `proxy_set_header Early-Data $ssl_early_data;`를 반드시 같이 넣고, 오리진은 `Early-Data: 1`이면서 비멱등 메서드면 `425`를 돌려준다. 헤더를 안 넘기면 오리진은 그게 0-RTT였는지 알 방법이 없다.

2. **`max_early_data_size`를 실제 필요한 크기로 잘라라.** `NewSessionTicket`의 `early_data` 확장 값이다. GET 헤더만 받을 거면 `16384` 대신 4KB 이하가 맞다. 0이면 그 티켓으로는 0-RTT 자체가 불가능하다.

3. **비멱등 요청에는 [[idempotency-key]]를 붙여라.** 키 단위로 결과를 기억하면 리플레이가 통과해도 상태는 한 번만 바뀐다. 0-RTT는 이걸 선택이 아니라 전제로 만든다.

4. **세션 티켓 키를 짧게 돌려라.** early data에 전방 비밀성이 없으니 STEK 수명이 곧 노출 창이다. 12~24시간 로테이션에 티켓 수명(`session_ticket_lifetime`)은 그보다 짧게. 키를 몇 달씩 고정한 채 0-RTT를 켜두는 게 최악이다.

5. **strike register 범위를 문서에 적어라.** "anti-replay는 PoP 로컬, 창 10초"처럼 명시해야 보안 리뷰가 된다. 안 적으면 개발자는 전역 보장이라고 가정한다. 그 가정이 위 시나리오의 출발점이다.

6. **효과를 먼저 재라.** 0-RTT가 아끼는 건 재접속 시 1 왕복뿐이고, 연결이 살아 있는 HTTP/2·HTTP/3 클라이언트엔 해당도 없다. p75 RTT 30ms 아래 국내 전용 서비스면 리스크 대비 이득이 작다.
